# 実タスク 3 条件評価（Skill なし / Agent Skills 型 / SkillSmith ビルド）

## 目的

SkillSmith の合成段（reuse / adapt / compose / provisional の判断と指針生成）が、実際の課題で価値を出しているかを確かめます。これは以後の全提案の採否を決めるゲートです。

## 現状の問題

事実: 現在の試験はモデルが固定値を返す構成で、指針が課題達成に役立つかは一度も測られていません。未測定: 達成率、誤適用率、needs_input の妥当さ、token 数のいずれも数値がありません。

## 提案

目的・受入条件・期待結果を付けた実タスクを 10〜20 件固定します。条件は (A) Skill なし、(B) Agent Skills 型（提案 02）、(C) SkillSmith ビルドの 3 つです。指標は受入条件の達成、誤適用（不適切な Skill の適用）、needs_input の妥当さ、入出力 token 数です。判定は人手ラベル、または提案 10 で較正した judge で行います。

## 検証（採用 / 不採用）

3 条件を同じタスク・同じモデル設定で走らせ、record を保存して再現可能にします。(C) が (B) をはっきり上回るなら合成段を維持します。上回らなければ合成段を縮小し、検索・版固定・失効・報告の層に絞ることを採用します。「はっきり」の閾値は、タスク数が少ないため事前に人が決めて本ファイルに記録します（仮定）。

## よくなったとみなす条件

(C) が (B) より受入達成が高く、誤適用が増えず、token 増が達成差に見合うと判断できることです。

## 悪化したとみなす条件

(C) が (B) と同等以下、または誤適用が増えることです。その場合は合成段を縮小する方針へ切り替えます。

## やらないこと

タスクを後から入れ替えて結果を良く見せることはしません。人の評価を自動指標だけで置き換えません。 本番の ContextStill への接続、語句辞書やキーワードによる意味分岐、費用上限によるゲートは行いません。推論は Grok Bot が recorded-inference の継ぎ目を通して行います。

## 依拠（コード・論文）

コード: `src/service/build.ts` の build 処理、`src/instructions/build.ts` の指示。論文: Agent Skills https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills 、ARES https://arxiv.org/abs/2311.09476 、CBR review https://arxiv.org/abs/2504.06943 （著者・全文は未確認）。

## 依存・前提

仮定: 評価用の実タスクと期待結果をユーザーが用意できること。前提: 提案 02、14。



## 実装結果

- **採否**: 部分採用（評価ハーネス）
- **内容**: 実タスク 10〜20 件のコーパスは未用意。代わりに 3 条件比較のスキーマ・比較関数・反証フラグを `src/eval/` に実装した。勝者のハードコードはしない。
- **パス**: `src/eval/task.ts`, `src/eval/compare.ts`, `src/eval/index.ts`, `src/test/eval-compare.test.ts`
- **試験**: `bun test src/test/eval-compare.test.ts`
- **未実施**: 実ユーザー課題コーパスの収集と (C) vs (B) の品質測定。品質スコアは主張しない。
- **理由**: ハーネス自体は正しく、製品挙動を退行させない。実タスクなしでは「よくなった」判定はできないため部分採用。
