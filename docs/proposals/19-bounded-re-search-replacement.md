# 再検索の飽和した作業集合を入れ替える

## 目的

初回の候補・文書枠が満杯でも、再検索で見つけた訂正資料が disclose / 選択へ届くようにします。提案 04 は一回の再検索を通すだけで、満杯時の入替と警告の維持は未対応です。

## 現状の問題

事実: 初回の candidate / document 予算が飽和すると、再検索の card は `cardsAdded=1` でも実際の追加は 0 になります。`sourceSearch` を置き換えると、残した資料の初回警告も消えます。これは Corrective RAG 型の訂正検索が構造的に効かない状態です。未測定: 実課題での訂正検索の優位。

## 提案

検索 round を識別し、発見 / 候補採用 / 本文取得の件数を分離します。満杯時にも再検索で見つけた資料を候補選択できる bounded working set を試します。適合の選択はモデルへ、回数 / byte / 版 / 重複の検査は構造へ置きます。残す資料には発見 round の警告・後継経路・版を保持し、最新 round で全消去しません。試験は candidates=documents=1、初回誤候補 / 再検索正候補、successor が枠を消費、同一 ref の異版、同じ後継への合流、初回 conflict → 二回目が空、を組み合わせます。

## 検証（採用 / 不採用）

構造試験の通過は安全と契約の採用根拠とし、実課題の品質は提案 16 で別途保留にします。悪化した場合は変更を戻し、不採用の理由を本ファイルに追記します。

## よくなったとみなす条件

正資料が実際に disclose / 選択へ到達し、警告が消えず、実消費が予約上限内であることです。

## 悪化したとみなす条件

必要根拠の追い出しや版の混合が起きること、呼び出し増だけで到達しないことです。

## やらないこと

無制限の top-k 拡張をしません。固定の語句による再 rank をしません。successor の版 pin 用 host API を発明しません。本番の ContextStill への接続、語句辞書やキーワードによる意味分岐、未確認の Eumenes host API の新設、自動正式公開、費用上限によるゲートは行いません。推論は Grok Bot が recorded-inference の継ぎ目を通して行います。

## 依拠（コード・論文）

コード: `src/service/build.ts` の候補結合、再検索、warnings の扱い。論文: [Corrective RAG](https://arxiv.org/abs/2401.15884)、[Gorilla](https://arxiv.org/abs/2305.15334)、[ToolLLM](https://arxiv.org/abs/2307.16789)。

## 依存・前提

提案 18 の外部境界を維持します。現行の fixture / SourcePort で構造試験は可能です。仮定: 入替で必要根拠を維持できること。
