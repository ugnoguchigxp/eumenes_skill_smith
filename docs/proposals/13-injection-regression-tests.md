# 取得文書への注入が構造検査で壊れることの回帰試験

## 目的

取得文書による権限拡張・役割変更・送信要求が、構造検査で必ず拒否されることを回帰試験で固定します。

## 現状の問題

事実: 構造検査は scope・capability・section を見ますが、注入文書を使った試験はありません。

## 提案

取得文書に権限拡張、役割変更、外部送信要求を含めた fixture を作り、モデルの出力がそれに従った場合でも `checkDecision` などで落ちることを試験します。モデルが従うかどうかは recorded-inference の記録で別に測ります。

## 検証（採用 / 不採用）

試験を追加して既存試験と一緒に通ることを確認します。構造検査がすり抜けたら、それを不具合として扱います。

## よくなったとみなす条件

すべての注入 fixture が構造検査で拒否されることです。

## 悪化したとみなす条件

試験が固定値に依存しすぎ、実際の注入経路を表していないことです。

## やらないこと

試験を通すために検査を特定文字列の検出に頼りません。 本番の ContextStill への接続、語句辞書やキーワードによる意味分岐、費用上限によるゲートは行いません。推論は Grok Bot が recorded-inference の継ぎ目を通して行います。

## 依拠（コード・論文）

コード: `src/service/build.ts` の `checkDecision`、`src/test/build.test.ts`。論文: Indirect Prompt Injection https://arxiv.org/abs/2302.12173 、Spotlighting https://arxiv.org/abs/2403.14720 。
