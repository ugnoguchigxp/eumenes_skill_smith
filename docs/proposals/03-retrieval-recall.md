# 検索 recall を合成とは別に測る

## 目的

検索段と合成段の失敗を分離し、どちらへ投資すべきかを判断できるようにします。

## 現状の問題

事実: 検索は lexical のみで、recall は単独で測られていません。未測定: 正解 Skill が候補に入る率。推定: 合成の失敗の一部は検索段の取りこぼしです。

## 提案

提案 01 のタスクごとに「使うべき Skill / 文書」を人手で付け、検索結果の recall@k を合成とは独立に記録します。

## 検証（採用 / 不採用）

採用判定は、提案 01 の固定タスク集合（未整備なら提案 14 の評価キット）で変更前後を同じ record から比較し、下の条件で決めます。悪化した場合は変更を戻し、不採用の理由を本ファイルに追記します。

## よくなったとみなす条件

recall の数値が得られ、合成失敗のうち検索起因の割合を説明できることです。

## 悪化したとみなす条件

ラベル付けの負担が評価全体を止めることです。その場合は件数を絞ります。

## やらないこと

recall を上げるために語句辞書や同義語表を入れません。 本番の ContextStill への接続、語句辞書やキーワードによる意味分岐、費用上限によるゲートは行いません。推論は Grok Bot が recorded-inference の継ぎ目を通して行います。

## 依拠（コード・論文）

コード: `src/contracts/ports.ts` の SourcePort / registry の検索操作。論文: ToolLLM https://arxiv.org/abs/2307.16789 、Gorilla https://arxiv.org/abs/2305.15334 。

## 依存・前提

前提: 提案 01、14。



## 実装結果

- **採否**: 採用（測定キット）
- **内容**: 人手ラベルの expectedRefs と検索カード列から recall@k を算出。製品の検索に意味ヒューリスティクスは入れない。
- **パス**: `src/eval/recall.ts`, `src/test/eval-recall.test.ts`
- **試験**: `bun test src/test/eval-recall.test.ts`
- **未実施**: 実タスクへのラベル付け。ラベル集合が来れば同じ関数で測れる。
- **理由**: 合成と独立に検索品質を数値化できる。製品挙動は変更していない。
