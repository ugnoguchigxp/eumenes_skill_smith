# キャッシュを考慮したJWKS鍵ローテーション計画

## 目的

キャッシュされたJWKSを使う検証側の可用性を守りながら、新公開鍵の先行配布、署名切替、旧公開鍵の保持、撤去を分離した実施計画を作る。製品固有のAPI・TTLは確定しない。

## 必須原則

署名に使う資格と検証用公開鍵の掲載資格は別に扱う。競合制御の成功は配布完了を意味せず、待機時間の経過だけもキャッシュ収束の証明にしない。必要な鍵の削除より段階の停止を優先する。

## 操作の境界

現在は文書作成だけを行う。将来の接続・変更は、対象と権限を管理者の承認記録で確定してから行う。公開JWKSには公開鍵のみを載せ、記録に秘密鍵や生トークンを残さない。漏えい対応の緊急失効は本計画の通常ローテーションとは分けて判断する。

## 標準ワークフロー

1. 実施条件を埋める。管理者の構成台帳・承認記録と、導入版の公式SDK／JWKSキャッシュ資料から、発行元、検証側の全経路、JWKS配信層、権限、署名アルゴリズム、トークン種別ごとの最大寿命、許容時刻差、キャッシュ更新・失敗時の動作を記録する。対象や権限が不明なら既存資料の収集までに留め、接続・変更は開始しない。寿命やキャッシュ上限が不明でも計画は作れるが、その値に依存する切替・撤去は許可しない。

2. 状態遷移と競合制御を設計する。状態を「旧署名中→新鍵配布済→新署名中・旧鍵保持→旧鍵撤去済」に分け、各遷移に世代番号と操作IDを持たせる。導入DB／鍵管理製品の公式仕様から、期待世代の比較と状態更新を不可分にする方法を選ぶ。新鍵登録と準備状態の確定は全成功か全取消とし、登録失敗で旧鍵の署名・公開資格を変更しない。旧行の更新が必要でも、公開対象から外す意味のinactive化と混同しない。競合で更新件数が0なら変更を打ち切って現在世代を再読込し、「配布完了」とは扱わない。仕様で原子性を保証できなければ変更を止める。参考例はこの段階ゲートのレビューに使う。

3. 新公開鍵を先行配布する。将来の承認済み作業では、既存kidを再利用せず新鍵を登録し、旧公開鍵を残したままJWKSへ新公開鍵を追加する。この時点では旧鍵で署名し続ける。登録の永続化、配信元と配信層における新旧kid・公開鍵の一致を観測する。登録失敗または結果不明なら署名切替はせず、操作IDと世代で結果を照合する。照合不能なまま再登録したり、旧鍵を消して帳尻を合わせたりしない。

4. 検証側の到達を判定する。事前承認した試験用の新鍵トークンと旧鍵トークンを用い、各検証系統・地域・配信層について、温まった旧キャッシュ、更新後、取得失敗時の挙動を試験する。通常の本番発行の切替とは分ける。kid不一致時の再取得は製品仕様に沿って回数制限・集約を設け、取得不能なら検証を迂回せず拒否する。対象全体の到達証跡、または仕様上の更新上限と試験による網羅的な根拠が得られなければ旧署名のまま待機する。無期限に古いキャッシュを使う検証側は、更新の確認か対象への再組込みができるまで切替不可とする。

5. 署名だけを新鍵へ切り替える。現世代と配布ゲートの成立を再照合してから、発行元ごとに署名kidを変更する。公開集合は新旧両方を維持する。各発行元の新kid出力、旧kidの最終発行時刻、検証エラーのkid別内訳を観測する。新鍵検証の失敗が出れば拡大を止め、旧鍵が安全に使用可能で承認されている場合だけ旧署名へ戻す。戻した場合も新公開鍵は残し、新鍵で既に発行したトークンを保護する。旧署名が再開したら旧鍵の保持期限を再計算する。

6. 旧公開鍵の保持期限を確定する。全発行元・待ち行列・遅延ジョブで旧署名が停止した証跡を集める。撤去可能時刻は、旧鍵トークンの最大expに検証側の許容猶予と時刻誤差上限を加えた保守的な最終受理時刻とする。最大expを漏れなく取得できなければ、旧鍵の最終発行時刻上限＋対象全種別の最大寿命＋同じ猶予・誤差で代替する。長寿命・オフライン利用も含め、上限を作れなければ旧公開鍵を保持して撤去を停止する。切替からキャッシュTTLだけ待つ方法で代用しない。

7. 保持期限超過後に撤去を独立承認する。現在世代、全発行元の旧署名停止、最終受理時刻の厳密な超過、次のローテーションが未着手であることを再照合する。成立した場合だけ対象の旧kidをJWKSから外す。他の保持中kidを巻き込む全置換はしない。撤去後は新鍵の正常検証とJWKS更新を観測し、失敗時は次の変更を止めて配信状態を調査する。遅れたキャッシュに旧公開鍵が残っていても、有効期限検証は緩めない。次周期は同じ排他管理を通し、前周期の記録と保持対象を引き継ぐ。各段階の承認、世代、kid、時刻、結果を記録して終了する。

## 完成条件

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 先行配布：登録の永続化とJWKSで旧・新両kidの存在を確認でき、対象となる全検証経路で新鍵の取得・検証が成立した場合のみ切替可能。登録失敗・到達不明・キャッシュ遅延では旧署名を継続する。
3. 競合：同一世代の並行要求では採用される新鍵が1つだけで、敗者の要求・失敗した登録・古い世代の要求が署名鍵や公開集合を変更しないこと。確認できなければ切替・撤去を停止する。
4. 保持・撤去：旧署名停止の全発行元での確認と、旧トークン最終受理時刻の保守的上限を超過した証跡が必要。旧署名再開、期限不明、時刻誤差不明、世代競合があれば撤去不可。
5. 将来の対象環境試験：保持期間内の旧トークンと切替後の新トークンが既存の検証条件で受理され、期限切れ・不正署名・解決不能なkidは拒否されること。新旧いずれかの正常検証が失敗した場合は次段階へ進まない。
