# URL取得機能のSSRF対策・検証計画

## 目的

ユーザー指定URLの取得機能について、SSRF防御の改修順序と検証計画を定義する。今回は文書作成のみとし、言語やクライアントが未定でも、実装選定時の合否と停止位置を定める。

## 必須原則

URL文字列の許可だけで接続を許可しない。全回答の分類と実際の接続先を結び付け、redirect・再試行・接続再利用でも境界を保つ。判定不能や部分的な検査成功を許可に変えない。

## 情報と通信の境界

将来の試験は所有者が承認したDNS・接続先・経路だけで行う。実metadataや第三者の内部サービスへの到達を試さず、隔離された模擬先と通信記録で遮断を検証する。応答本文やLocationは未信頼入力とし、ログにURL認証情報・秘密のquery・本文を残さない。

## 標準ワークフロー

1. 実装着手前に、所有者から対象コード、言語と版、DNS resolver、HTTP clientと版、proxy・egress・接続pool構成、試験権限を入手する。各公式文書で「自動redirect停止」「全A/AAAA取得」「接続IP固定とhostname/TLS検証の分離」「実peer観測」「全体期限とストリーミング中断」の可否を対応付ける。不能な項目があれば取得経路の変更を設計し、その能力が確立するまで実接続と公開を止める。既存資料の読解まで禁止しない。現時点ではコード実行・ファイル操作・通信を行わない。
2. DNSより前に、対象clientと意味が一致するURL parserで一度構造化し、その構造から送信先を作る。許可schemeはHTTP/HTTPSのみ、userinfoは空の記載も含め拒否する。host必須とし、大小文字・末尾ドット・IDNAの扱いを統一してlocalhostとそのサブドメインを拒否する。数値IPは同じIP分類へ渡す。曖昧なIPv4表記、zone ID、制御文字、backslash、二重decodeやparser間で宛先が変わる入力は拒否する。ポートの許可集合も用途に応じ決定する。scheme、userinfo、構文、名前の拒否時はDNSも接続もゼロを期待値にする。URL全体の文字列置換で正規化しない。
3. 名前は要求時に信頼するresolverでA/AAAAを取得し、関連する別名解決を経た全回答を分類する。一つでも禁止IPが混在した回答、空回答、解決失敗、回答の完全性が判定不能な場合は、その段の接続前に拒否する。IPv4 mapped IPv6は内包IPv4に正規化して同じ規則を適用する。loopback、private、link-local、ULA、CGN、multicast、未指定、予約・特殊用途と環境固有の内部範囲を拒否する。metadataは169.254.169.254だけに限定せず、クラウド所有者の資料からIPv6・固有IP・名前も列挙する。分類表はIANAの特殊用途レジストリと対象ネットワーク設計に照合し、単独のis_global判定を最終仕様にしない。内部範囲やmetadata一覧が未確定なら既存構成資料を収集し、対象ネットワークでの有効化を止める。
4. 検証済み回答の一つへ接続を固定し、clientによる別の名前解決を許さない。HTTPのHost、HTTPSのSNI・証明書検証名は元の検証済みhostnameを保持する。実peerが許可集合と選択先に整合しない場合は、HTTP要求を送らず切断する。事後検知だけをrebinding対策にしない。再試行やIPv4/IPv6の並行接続も検証済みIPだけを候補にする。pool再利用・HTTP/2接続共用がこの対応を崩さないか検査し、保証不能なら無効化する。proxy利用時は手元peerがproxyであることを区別し、proxy側の解決・最終接続先制約と記録を必須にする。保証がなければその経路を使用しない。egress制御を独立した防壁に追加する。
5. 自動redirectを止め、Locationを現在URLに対して解決した結果を手順2から再評価する。各段のDNS・接続固定・peer検証を省略しない。禁止段で止まっても、それ以前の許可段のDNS・通信は許可済み作用として区別する。redirect回数の上限超過、循環、不正Locationで追跡を停止する。別originへ認証headerやCookieを転送しない。
6. 所有者がDNS・接続・TLS・応答待ちの段階上限、redirectと再試行を含む全体期限、header量、受信本文量、展開後本文量、redirect回数を具体的な数値・単位で承認するまで本番有効化しない。全体期限は単調時計に基づき、各段へ残時間を配分する。Content-Lengthを信用せず、chunkedや圧縮応答も逐次計数し、超過時は読取りと接続を中断して部分結果を成功として返さない。低速の小分け送信で期限が延長されない設計にする。
7. まず通信なしの合成試験を設計する。references/stage-fixture.mdは拒否段階と先行作用の期待値を読むために使う。対象実装の試験には全回答混在、IPv6のみ、mapped IPv6、末尾ドット、userinfoの符号化、非標準IPv4表記、許可→禁止redirect、相対Location、循環、解決後の回答変更、許可集合外peer、上限ちょうどと超過を含める。各ケースでDNS照会・接続試行・HTTP送信・応答読取りの回数と停止理由を記録する。誤許可や過剰拒否が出れば分類・parser差・接続経路を見直す。
8. 合成試験が期待どおりになった後、明示的な許可を得た隔離環境で実接続試験を計画する。管理下DNSで複数A/AAAAと回答切替を再現し、管理下HTTP/HTTPSでredirect、遅延、巨大・圧縮応答を返す。packet/egress記録とclientのpeer記録を照合し、再試行・pool・proxy・TLS hostname検証を含める。実内部サービスや実metadataへ試験要求を送らない。拒否先の到達有無を観測できない、権限がない、上限が未決定ならそこで止め、試験結果と未測定項目を分けて記録する。全経路の合否が揃うまで公開しない。

## 完成条件

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 計画書：URL→DNS→接続→応答→redirectの順序、各拒否位置、上限の決定者と実環境検証項目が明記されれば完成。現在の外部操作や実測成功を含めない。
3. 合成試験：参考例の全assertが成立することを将来確認する。未実行の例であり、対象実装の合格証明にはしない。対象実装では同じ正負ケースに加え、本文記載のURL表記差・制限境界を検査し、期待する停止段階と作用が一致しなければ改修へ戻る。
4. 実接続試験：許可済み試験先に限り、各段の全DNS回答・選択IP・実peer・redirect履歴・経過時間・受信量を照合する。禁止IPへの接続ゼロ、peer不一致時のHTTP送信ゼロ、認証情報付きURLのDNS照会ゼロ、各上限超過時の中断を証明できなければリリースを止める。先行する許可済み段の通信は失敗に数えず、拒否対象段への通信を区別する。
