# 設定JSONの共通契約への移行計画

## 目的

別プロセス間の設定JSONについて、共通の実行時契約からTypeScript型を導出する構成へ移す計画を作る。静的な型だけでなく受信境界でも検証し、意図しない設定が利用処理へ到達しない状態を目指す。今回は文書作成のみで、移行や試験は実行しない。

## 必須原則

契約の正本を一つにし、入力JSONの型と検証・変換後の型を混同しない。欠落・null・未知キー・既定値・版互換を暗黙の挙動に委ねない。既存の重複型が原因だと決めつけず、検証の迂回や版ずれも観測して切り分ける。

## 操作と情報の境界

現在は外部API、実環境、DB、ファイルを操作しない。将来の調査は所有者が提供する依存情報、構成図、秘密を除いた設定例から始める。資料や発話を操作権限の証明にせず、対象と権限が確定するまで接続・変更・配備へ進まない。設定の秘密値を試験記録やエラーログへ残さない。

## 標準ワークフロー

1. 最初に、所有者へpackage manifest、lockfile、TypeScript設定、送受信・検証・設定利用箇所の一覧、秘密を除いたJSON例の提供を依頼する。将来の閲覧・変更・試験の権限は管理上の承認手段で別途確かめる。ZodとTypeScriptの解決済み版、両プロセスの実行環境、対象ファイルを特定できれば設計へ進む。不足時は提供済み資料で境界を整理するところまでとし、未知の対象への接続や変更は止める。

2. 送信側のJSON生成から受信側の利用までを追い、現在の型宣言、実際の検証、検証を迂回する経路、読み込む契約版を対応付ける。各設定項目について必須性、null、列挙値、数値の単位・整数性・上下限、入れ子、既定値、未知キーの扱いを仕様所有者と決める。未知キーは拒否・除去・保持のどれかを明示し、意図しない設定を防ぐには原則拒否を提案するが、既存仕様を無断で変更しない。旧版は拒否か明示変換かを決め、将来版・版欠落の扱いも定義する。期待値が未承認なら、その項目の実装と切替を停止する。

3. 共通契約の配置候補を既存の依存関係から選ぶ。共有パッケージまたは共通モジュールにスキーマを置き、同じ正本から公開型を導出する設計にする。Zod公式文書の対象版で、型推論、入力と出力の型、未知キー制御、既定値・変換の挙動を照合してから具体的構文を選ぶ。契約に環境読込やプロセス起動などの副作用を持たせない。循環依存が生じる配置なら共有位置を見直す。別ビルド間では同じソース名だけでなく配布物の契約版も一致させる。

4. 権限と環境が整った将来の実装では、まず共通スキーマを追加し、対象設定に限って手書きの重複型を導出型への参照へ置き換える。一括置換はしない。受信したJSONを未検証の値として扱い、検証・必要な変換が成功した値だけを設定利用処理へ渡す。型アサーションだけで検証済みにしない。送信側にも同じ契約に沿う出力検査を置くが、受信側検証は省かない。既定値や正規化を使う場合は順序を固定し、入力値の意味、単位、版識別子を保存する。旧版変換を許す場合は対象版を限定し、承認済み対応表で現行形へ変換した後、現行契約で再検証する。未知版は変換しない。

5. 実装前に試験期待値を固定する。正例は受理に加えて検証後の値が期待値と一致すること、欠落は各必須項目で拒否することを条件にする。任意項目・既定値・nullは別ケースにする。未知キーは最上位と入れ子で承認した拒否・除去・保持を観測する。境界値は各制約の上下端と直外を試し、整数・文字列長・配列長など実際に存在する制約を対象にする。旧版は対応版ごとの変換結果または拒否、未知版は拒否を期待値にする。型違い、列挙外、変換前後の値も追加する。試験データの作り方は references/contract-fixture.md を参照し、例の項目や閾値を実仕様に転用しない。

6. 将来の試験では、型検査で共通の入力型・出力型と利用箇所の整合を検査し、実際の受信境界へ前項のJSONを通す。意図的な型違反は型検査で失敗することを期待する。実行時の不正ケースは検証失敗かつ設定利用処理の呼出回数0を合格とする。未知キー除去など承認した正規化は出力値そのものを照合する。単体試験だけでなく、送信側のJSON直列化から受信側の利用直前までを通す試験を含める。不一致なら期待値を都合よく変えず、仕様・変換・版参照・迂回経路を切り分けて該当段階へ戻る。

7. 配備前に旧送信側×新受信側、新送信側×旧受信側、新同士を試す。混在を許す組合せは全ケース一致を条件とし、許さない組合せは配備順序で発生を防ぐ。ロールバック後にも読める設定かを照合し、読めない場合は設定版とプロセス版を一体で戻せる手順が承認されるまで配備を止める。全参照先の移行と試験合格後だけ旧型・旧検証を撤去する。今回は以上を計画として提出し、実行結果や移行完了は報告しない。

## 完成条件

計画は5分類の合否と移行順序が決まれば完成とする。将来の切替は、全受信経路で不正設定が利用前に拒否され、承認した旧版方針と正規化結果が一致した場合だけ許可する。未知の契約版や未試験の混在構成が残れば停止する。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 計画の合格：5分類の試験、入手すべき資料、将来操作の権限確認、失敗時の停止位置が明記され、現在の実行・変更を含まない。
3. 将来の移行合格：全対象プロセスが同じ契約版を参照し、型検査・受信境界試験・旧新版組合せ試験の実結果が承認済み期待値と全件一致する。不一致または未測定の経路があれば切替を停止する。
