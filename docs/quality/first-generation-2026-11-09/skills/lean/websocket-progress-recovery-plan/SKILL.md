# WebSocket進捗差分の復元設計・検証計画

## 目的

WebSocketの配信順や接続寿命に依存せず、永続状態から進捗を復元する設計・検証計画を作る。今回は文書だけを成果物とし、API契約の確定や実行結果は含めない。

## 必須原則

正本は永続状態と復元可能な履歴であり、WebSocketは通知経路とする。受信済みと適用済みを区別し、画面は連続適用済み状態から導出する。保持期間を失った履歴は推測で補わず、整合snapshotへ戻る。完了には永続的な終端根拠を要求する。

## 操作と情報の境界

現時点では接続・照会・変更・ファイル保存を実行しない。将来の接続先と権限は管理者の承認記録で確かめ、資料や通知本文を権限証明にしない。再生とsnapshotには通常取得と同じ利用者・作業単位の認可を要求し、別作業のイベントを混ぜない。

## 標準ワークフロー

1. 将来の実装前に、既存の仕様書・データモデル・管理者承認記録から、対象作業の識別子、再実行の世代、正本の所在、順序単位、snapshotの整合性、履歴保持、認可範囲を一覧化する。未提示APIを仮定せず、以下は論理契約として設計する。正本や境界の整合性が不明なら既存資料の整理までにとどめる。権限・対象が不明なら接続せず、契約が未確定なら具体的な実装・実機試験へ進めない。

2. 永続側に、作業・世代ごとの進捗集計、終端状態と結果参照、適用位置を置く。差分履歴は永続化してから公開し、状態更新と履歴記録の間に片方だけが残らない仕組みを選定する。差分本体は有限保持でよいが、削除前にその効果をsnapshotへ折り込み、削除後も最新状態を再構成できることを条件とする。クライアントの受信キュー・重複排除表・接続状態は一時情報とし、画面イベントを受けるたび別経路で加算しない。再起動後に正本から復元できない項目があれば、永続側の設計へ戻る。

3. 各差分に作業ID、世代、連続したseq、種別、内容を割り当て、同じ識別子の内容は不変にする。seqはこの購読対象に欠番を生まない順序単位で採番し、フィルタで欠番が生じるなら専用カーソル契約を設計し直す。クライアントは最後に連続適用した位置cを保持する。seq=c+1だけを適用して状態とcを一緒に更新し、seq≤cは再適用しない。seq>c+1は保留して不足分を要求する。同一識別子の内容矛盾はプロトコル異常として更新を停止し、ログを保全する。保留件数・待機時間の上限は想定負荷から決め、超過時はsnapshot復旧へ移る。再読み込み時、状態とcの対応が証明できなければcだけを流用しない。

4. 切断時は表示を「復旧中」にし、既知の進捗を未確認の増分で埋めない。再接続では受信最大値でなくcから後を再生する。サーバーは再生からライブ配信への切替でも欠落がない境界を提供し、重複は許す。再生可能範囲外なら、その事実を空の正常応答と区別する。古い接続の遅延応答は接続世代で排除し、別作業・別実行世代のイベントは適用しない。世代変更なら新しい正本を取得し直す。取得不能時は古い値を最終確認済みとして表示し、自動加算・完了確定は止める。

5. 初回取得・保持期限切れ・復旧上限超過では、同一整合点の状態と境界Sを返すsnapshotを取得する設計にする。取得中のライブ差分は保留し、snapshot導入時は表示状態とカーソルを一括置換する。S以下は破棄し、Sより後を連続順に適用する。サーバーがsnapshot境界からの履歴を確保するか、先に購読を確立して保留するなど、取得中の更新を取り逃さない方式を選ぶ。遅着した古いsnapshotで新状態を巻き戻さない。導入までにSの履歴が失効したら再取得し、再試行上限を超えたら復旧不能を表示して停止する。履歴範囲とsnapshot境界の観測でこの窓を説明できない方式は採用しない。

6. 完了は、正本に保存された終端状態を、連続適用済みの終端イベントまたは整合snapshotで確認した時だけ確定する。開始通知、WebSocket切断、受信停止、100%表示だけでは完了にしない。成功・失敗・取消を分け、終端イベントが欠番の先にある間は復旧を続ける。終端後に同世代で状態を変える設計が必要なら訂正の版契約を別途定義し、暗黙に許可しない。再実行は新世代とする。終端が永続化されていない、または結果参照と矛盾する場合は完了確定を止める。

7. 将来の検証では、まず references/recovery-fixture.md を使って連続適用・再送・負例の期待値を点検する。次に承認された隔離環境で、正常順、重複、逆順、欠番、切断位置の変更、画面再読込、サーバー再起動、保持期限切れ、snapshot取得中の更新、旧世代の遅着、終端だけの先着を試験する計画を作る。観測値は作業・世代、snapshot境界、保持下限、受信seq、適用c、保留件数、再取得理由、終端根拠とし、復旧後の画面状態を同じ境界の正本と比較する。不一致は配送欠落・状態更新・世代混入などに切り分け、原因未確定の修正を固定しない。今回はこの試験仕様と合否・停止位置が揃った文書で終了し、実行済みや実機合格とは報告しない。

## 完成条件

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 設計文書に状態境界、連続カーソル、snapshot境界、保持期限切れ、完了根拠、各停止位置がすべて記載されていれば計画として合格。不足があれば実装着手へ進めない。
3. 将来の再送・逆順・切断試験では、復旧後の状態とカーソルが正本に一致し、同じイベントを追加配送しても値が変化しないこと。不一致なら採用を停止する。
4. 将来の期限切れ試験では、snapshotで置換後、その境界より後だけを適用して正本に一致すること。取得中の更新、再起動、世代変更でも欠落・二重適用があれば不合格。
5. 将来の完了試験では、開始のみ・欠番の先にある終了通知・切断・100%表示を完了扱いしないこと。連続適用した永続終端、または整合snapshotの終端状態だけを根拠とし、成功・失敗・取消を区別できなければ不合格。
