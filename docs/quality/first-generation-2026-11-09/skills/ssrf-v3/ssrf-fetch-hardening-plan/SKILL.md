# URL取得機能のSSRF防御・検証計画

## 目的

ユーザー指定URLを取得する機能について、入力から実通信までSSRF防御を維持する改修・検証計画を作る。現在は文書作成のみとし、実装・接続・試験の成功は主張しない。

## 必須原則

URL文字列の検査だけで通信を許可しない。解決結果は全件判定し、許可した接続先と実際の通信経路を結び付ける。再試行・redirect・接続再利用にも同じ境界を適用し、保証できない経路は拒否する。

## 試験と情報の安全性

将来の通信試験は所有者が承認した隔離環境と管理下の宛先に限定する。本物のmetadataや第三者の内部サービスを試験先にしない。取得本文・Location・DNS応答は未信頼入力とし、ログへ認証情報や本文を保存しない。

## 標準ワークフロー

1. 将来の実装前に通信経路を棚卸しする。リポジトリと依存関係台帳から言語・版・URL parser・resolver・HTTP clientを、運用設定からproxy、接続プール、再試行、egress経路を特定する。所有者から変更権限と試験対象の承認を取得する。版別公式文書で、解決先指定、TLSのhostname検証、redirect無効化、stream中断、peer観測の契約を照合する。未特定なら既存記録の調査までとし、対象不明の接続・変更は開始しない。必要な制御がないclientは採用を見直す。

2. URLの受入境界を実装する計画を立てる。共通parserで一度解析し、その解析結果を後段へ渡す。絶対URLのhttp/httpsだけを許可し、userinfoは空の表記も含め拒否する。空host、不正なport、制御文字、曖昧な数値IPやparser間で解釈が変わる表記は拒否する。hostだけを対象に大文字小文字・末尾ドット・必要なIDNAを正規化し、path/queryを全置換しない。正規化後のlocalhostとそのサブドメインを拒否し、IPv6 zone IDも拒否する。scheme・userinfo・hostで不合格ならDNSも接続も行わない。許可portは用途に合わせて明文化し、暗黙に全portを許さない。

3. 宛先ポリシーを定義する。IP literalは直接、hostnameは要求時に得た全A/AAAAを分類する。resolverの片方だけ成功した結果や候補の一部だけで許可せず、空応答・エラー・不完全取得は拒否する。IPv4 mapped IPv6はIPv4へ正規化して同じ規則を適用する。private、loopback、link-local、CGN、ULA、multicast、unspecified、予約・特殊用途範囲に加え、組織固有の内部経路とクラウドmetadataのIP・名前を拒否対象にする。現在のIANA特殊用途レジストリ、利用クラウドの公式metadata資料、管理者のネットワーク台帳から規則を確定する。単一のis_private判定だけに依存しない。候補に一つでも禁止先があれば接続前に全体を拒否する。追加のIPv6移行・変換経路は到達先を安全に判定できなければ拒否する。

4. DNS判定と接続を不可分にする。検査済み集合から選んだIPへ接続先を固定し、clientによる再解決を許さない。元のhostnameはHTTPのHostとHTTPSのSNI・証明書hostname検証に維持する。各接続のpeerが選択したIPと一致し、禁止範囲でないことをアプリケーション要求送信前に判定する。候補切替・再試行・接続再利用・HTTP/2の接続共有にも宛先単位の対応を保つ。透過proxyや環境変数proxyで別経路になる場合は無効化するか、proxy側にも同等の解決・宛先制御を要求する。peerがproxyであるだけでは最終宛先の証明にならない。固定や送信前検査が不可能ならその取得経路を停止し、対応clientまたは管理されたegress方式へ設計を戻す。ネットワーク側でも内部・metadataへのegressを遮断するが、アプリ側検査の代替にはしない。

5. 自動redirectを無効化し、Locationを現在URLに対して解決した次URLごとに手順2〜4を適用する。相対URL、別host、scheme変更も例外にしない。前hopへの許可済み要求は許されるが、不合格の次hopには要求を送らない。認証ヘッダー・cookieなどの機密情報は別originへ転送しない。redirect回数、全hop・DNS・再試行を含む総期限、DNS/接続/TLS/読取待ちの期限、headerとbodyの上限を設定表に数値・単位で定義する。圧縮前と展開後の両サイズをstreamで制限し、Content-Lengthの有無を信用しない。上限超過時は読取・展開・再試行を打ち切り接続を解放する。値はサービスの応答要件と容量予算から所有者が承認し、未設定なら取得を有効化しない。

6. 接続しない合成試験を先に設計する。references/offline-policy-fixture.mdを停止段階の最小例として読み、実装のparser・分類・制御フローへテストを追加する。混在A/AAAAと順序入替、全件公開、空応答、mapped IPv6、localhostの大小文字・末尾ドット、metadata、userinfo、非HTTP、曖昧IP、相対redirect、多段・循環redirectを含める。resolver/clientのテスト用差替えでは解決後の候補変更、peer不一致、再試行時の再解決を注入し、拒否段階以後の作用がないことを履歴で比較する。時間・サイズは境界値、超過、遅延stream、chunked、圧縮展開を扱う。最小例はポリシーモデルであり、実装試験の代わりにしない。不一致は該当段階の実装へ戻す。

7. 権限と隔離環境が揃った後だけ実接続試験へ進む。管理下のDNSとHTTP/HTTPSサーバーで複数回答、回答の切替、redirect、遅延、過大応答を再現する。禁止先は隔離した模擬宛先で代替する。resolver履歴、接続先、要求受信記録、egressログ、経過時間、読取量を関連付け、rebinding時にも固定先以外へ接続しないこと、TLS検証を維持すること、全再試行・再利用経路で制約が続くことを観測する。期限超過時に裏で処理が継続しないことも測る。観測不足なら合格にせず計測設計へ戻し、想定外通信なら試験を中止・保全する。全対象経路が合格してから別途承認された段階公開を計画し、拒否理由・上限超過・接続先不一致を機密なしで監視する。今回は以上の計画文書で終了する。

## 完成条件

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 計画の完成：全入力種別、全A/AAAA、redirect、実接続先、rebinding、時間・サイズに対し、実装箇所・観測・拒否段階が対応していること。欠落があれば計画を修正し、実装開始へ進まない。
3. 合成試験：参照例の正負ケースが期待した停止段階と作用履歴に一致すること。将来の実装テストでは手順6の追加ケースも一致させる。不一致は実接続試験へ進めず修正する。
4. 実接続試験：承認済み試験先で、全候補の分類、固定したIPとpeerの一致、各redirectの再判定、禁止先へのアプリケーション要求ゼロ、設定した各時間・容量上限での中止を観測できた経路だけ合格。観測不能・超過・想定外接続は公開を止める。
