# 初回SKILL生成の比較と配達接続の検証

SSRF対策は監査を分離した版で、本文と参照ファイルを含めて配達できた。標準処理は68.64秒で99点、高速処理は50.28秒で98点だった。今回の完成品8本で最短は50.28秒。初回の完全な配達を2〜3秒に収める目標は未達。技術評価は77.9点から78.9点へ上がった。

## 約60秒と途中終了の原因

前回の3課題で、本文生成1回だけに48.73〜54.86秒かかった。今回の従来経路でも、完成したJSON契約の本文生成は52.46秒、失敗したWebSocketの本文生成は53.90秒だった。検索、資料開示、意味審査の時間を加えると約60秒になる。API応答待ちの実測なので、提供側のキュー、推論、通信の内訳は分からない。

前回のSSRFは提供元が `max_output_tokens` を返し、4,000出力トークンで監査の `sourceReview` の途中までしか返さなかった。今回もWebSocketの従来経路とSSRFの中間版は、本文と例の後に監査を生成している途中で同じ上限に達した。SSRFの別の中間版は3,771トークンで完結したが、最初の許可済み送信まで一律に禁止する合否条件を含み、意味審査が配達を拒否した。時間切れ、生成出力上限、意味審査の拒否を別々に記録した。

変更は選択可能な `Ports.assemblyMode: "lean"` にまとめた。

- 権限の範囲にある上位2候補までを、既存の資料取得・版照合・予算の範囲で先に渡す。ほかの候補を読むか、資料を使えるかはLLMが判断する。初期開示に別の推論が必要だった場合は1回分減る。
- 手順本文は `localizedInstructions`、合否は `verification` に一度だけ書く。見出しだけを持つ節には本文を入れられない形を提供元の出力形式にも示す。段階ごとの作用と対象を照合してから、負例の合否を確定する。
- `sourceReview` と `nonSourceAdditions` を本文生成の応答から外した。既存の意味審査が全ファイルと資料を照合し、承認時に両方を返す。監査が揃わなければ配達を拒否する。意味審査へ渡す本文・参照も各1回に整理した。
- 4,000出力トークン、原条件、版・権限の検査、全ファイルの意味審査を試験条件に維持した。承認済み成果物・保存済み結果の版互換のため、既存ホストの既定値は `baseline`。新経路はホストが明示選択する。

## 配達接続

Eumenesが公開する推論操作とジョブ・ストアを同じ一時DBで組み合わせた。推論の予約、受領証と使用量の取得、要求と受領証の照合、本文と参照の配達が通った。別の依頼の受領証と取消済みの受領証は拒否された。モデル応答・資料・利用者権限は試験用の値で、外部通信は別のクラウド比較で測った。[接続試験](eumenes-inference-delivery.json)

稼働中のEumenesではジョブ一覧と機能一覧が認証を要求した。稼働中のContextStill v1は検索を公開しているが、版を再確認して本文を取得する操作がない。v2のソースには取得操作があるものの、検索結果の版と、取得時に本文が切り詰められたかを照合できる契約が不足している。本番配達には、この資料契約と認証済みの検証経路、および本体への登録が必要。[稼働環境の確認結果](live-contract.json)
