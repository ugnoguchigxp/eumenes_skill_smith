# 管理画面のパネル状態遷移とフォーム関連付けの独立レビュー計画

## 目的

詳細画面の遅延表示パネルと、別画面の設定フォームを独立してレビューできる計画を作る。各経路で表示・操作・関連付けの期待値と観測結果を対応させ、合否または未測定を残す。

## 必須原則

取得状態と開閉状態、状態と再試行操作を分けて扱う。見た目の隣接を意味上の関連付けの証拠にせず、実際の対象画面・現在の名前・説明を根拠にする。二つの経路の成否を相互の前提にしない。

## 実行境界

現在は文書作成のみとし、外部API・実環境・DB・ファイルへの操作やテスト実行は行わない。将来も、資料や発話だけを権限証明にせず、対象範囲と許可を正式な承認記録で照合する。設定の保存や実サービスへの失敗注入をレビューの暗黙の一部にしない。

## 標準ワークフロー

### 共通の準備
1. 現在は本計画の作成だけを行う。将来の担当者は、対象変更の版、画面の経路、許可された検証環境と操作範囲を、変更管理記録・環境管理者の承認記録から照合する。対象または許可が一致しなければ接続・変更を開始せず、その不足の解消へ戻る。すでに提供された資料のレビューと、権限を要する実環境へのアクセスは区別する。
2. 将来、対象リポジトリの依存定義・ロック情報、画面仕様、既存テストからDOM構成とテストライブラリの版を取得する。使用予定の観測・応答制御機能をその版の公式文書と照合し、利用可能な場合だけ具体的テストへ落とす。機能が不明なら推測したAPIを使わず、その機能が必要な項目を停止する。参考例 references/review-oracle.md は判定条件の点検用であり、対象画面の代用ではない。

### 手順A：詳細画面の遅延表示パネル
1. 詳細画面だけを対象に、パネルが存在する経路・対象データ・開く操作を特定する。仕様から取得中、成功、失敗の表示内容、再試行の有無、閉じる操作を期待値として記録する。期待値が対立する項目は仕様責任者へ戻し、その項目の合否を確定しない。
2. 許可された隔離環境で、成功・失敗・保留を個別に返し、到着順を制御できる既存のテスト手段を選ぶ。外部の実サービスを変更せず制御できることを開始条件とする。できなければ通常の画面観測までに限定し、遅延・競合の検査は停止する。記録には開閉状態、要求識別子、到着順、表示内容、操作可否を含める。
3. パネルを開き応答を保留する。取得中表示、成功・失敗表示の残留、閉じる操作と再試行操作の可否を観測する。その後成功応答を到着させ、返した合成データが表示され取得中表示が解消するかを期待値と照合する。固定時間の待機だけで合格にせず、テスト環境で定めた上限内の状態変化を観測する。上限超過は記録して停止する。
4. 独立した初期状態から失敗応答を返し、エラー表示と再試行手段を観測する。再試行を操作し、新しい要求、取得中表示、成功応答後の回復を順に記録する。要求が発生しない、前のエラーだけが残る、重複要求が仕様外に増える場合は不一致として原因調査へ戻る。原因未確定のまま状態管理の修正方式を指定しない。
5. 要求を保留したまま閉じ、旧要求の成功応答を到着させる。別の初期状態から失敗応答でも繰り返す。閉じた状態の維持と、見えない旧結果による再表示がないことを観測する。続いて閉じた後に開き直して新要求を成功させ、旧応答を後着させる順序でも新内容が維持されるか検査する。内部キャンセルの有無だけで合否を決めない。
6. 各ケースの初期状態・イベント順・期待値・実測値を保存する計画とし、不一致は再現条件を絞って再観測する。仕様変更なら期待値を承認し直す。パネルの判定が完了または未測定で確定した時点で、この経路を終了する。

### 手順B：別画面の設定フォーム
1. パネルの成否に依存せず、設定フォームの画面経路、対象入力一覧、表示条件を特定する。入力ごとに期待するラベル、エラー文、通常ヘルプを仕様と照合する。対象入力が存在しない状態なら正しい画面・状態へ戻り、名前だけで別画面の入力を代用しない。
2. 許可された検証環境で、DOMとブラウザーのアクセシビリティ情報を観測する。各入力の計算済みアクセシブル名を期待ラベルと比較し、明示ラベルなら参照先IDの存在・一意性、内包ラベルなら実際の対象入力、ARIAによる名前なら参照先と優先関係を追う。見た目が同じでも別入力を指す場合は不一致とする。
3. 実保存を伴わない既存の検証手段で、各入力のエラーと複数入力の同時エラーを作る。送信が必要で、その作用が許可範囲外なら送信せずこの項目を停止する。エラー表示中は各入力の説明参照と計算済み説明を追い、対応するエラー本文が含まれるか、参照先が存在するか、別入力のエラーが混入しないかを記録する。共有エラーは仕様で共有対象が明示されている場合だけ許容する。
4. 一つの入力だけを有効値へ直し、検証を再評価する。解消したエラーとその参照が残らず、他入力の未解消エラーと通常ヘルプが維持されるか観測する。DOM上の文字列だけでなく入力側の名前・説明を再取得する。
5. 入力ごとの期待値・DOM上の関連先・計算済み名前と説明・不一致を記録する。不一致は該当入力だけで再現し、未提供のDOMや版を推測して全置換しない。全対象の判定、または不足情報と停止項目の確定で、この経路を終了する。

## 完成条件

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. パネル：取得中・成功・失敗・再試行の各表示と操作可否が承認済み仕様に一致し、失敗から新しい取得を経て成功する記録があること。閉じた後に旧応答の成功または失敗を到着させても再表示されず、新しい表示内容を旧応答が上書きしないこと。不一致は不合格、応答順序を制御できない場合は該当項目を未測定として終了する。
3. フォーム：対象入力すべてで期待したアクセシブル名が得られ、ラベルの対象が一意であること。各エラーが対応する入力の説明に含まれ、別入力のエラーが混入せず、解消後に古い説明が残らないこと。不一致は不合格、DOM・アクセシビリティ情報を取得できない項目は未測定として終了する。
4. 計画文書：二つの独立した経路、将来の開始条件・停止位置、観測対象と期待値、参照コードの正例・負例が揃えば完成。参照コードは未実行であり、その静的整合や将来の成功を実画面の合格に数えない。
