# JSON契約移行とCSV設定インポートの独立運用計画

## 目的

リリース前に、共通JSON契約の移行と別バッチのCSV設定インポートを、それぞれ開始・停止・復旧・承認できる運用計画にする。現在の成果物は文書であり、実行結果や実環境の合格証明ではない。

## 必須原則

互換性と復旧可能性を契約移行の判断軸とする。CSVは全候補の検証とテナント境界を優先し、異常を含むバッチを部分適用しない。両経路の接続、同一格納先、共通の変換形式は仮定しない。

## 操作と情報の境界

今回は外部API・実環境・DB・ファイルへの操作を行わない。将来の接続先と変更権限は管理者の承認記録で確定し、参考資料や発話を権限証明にしない。CSVに含まれるテナント識別子を認可の根拠にせず、エラー記録へ設定値や秘密情報を不用意に転記しない。

## 標準ワークフロー

1. **二つの審査票を起こす。** JSON契約移行とCSVインポートについて、担当者、承認者、対象環境、開始条件、期待差分、停止・復旧担当を別々に記入する。現時点では文書上の未確定事項を列挙するだけとし、接続や読取りも実行しない。将来、環境管理者から接続先識別情報と権限の承認記録を入手し、対象と操作種別が一致する場合だけ当該操作へ進む。不一致ならその接続・変更を止めるが、既に提供された資料の整理は続けられる。

2. **JSON契約の比較と変換仕様を作る。** リポジトリ管理者から現行・移行先スキーマ、シリアライズ／読取り実装、版一覧、匿名化した既存設定例を入手する。必須項目、型、null・欠落・既定値、未知フィールド、単位、版識別を比較し、旧／新の利用側と既存／新規設定の組合せごとに期待結果を定義する。名称・型・単位の変換は対象パスを限定し、対象外フィールドと識別子を保存する。旧新キー併存、情報損失、変換不能値の扱いが未決なら移行仕様を確定せず、全置換や推測による補正は行わない。

3. **JSON経路の適用順を固定する。** 将来の隔離環境で、復元可能な退避と復旧リハーサル、必要な旧新読取り互換の導入、承認対象だけの変換予行、限定適用、段階的展開、新形式の書込み有効化の順を基本として設計する。実装が別の順序を要するなら、各段階で稼働する読取り側・書込み側の版と互換性試験結果を根拠に順序を承認し直す。各段階で対象件数、対象外不変、読取り結果、競合を観測する。不一致なら次段階を止め、変更済み対象を保全して復旧担当へ渡す。復旧後に新形式の書込みが失われない扱いも決める。旧形式対応の撤去は旧版利用の終了と復旧保持期間の満了を根拠に別承認とする。

4. **CSVの形式と許可範囲を独立に定義する。** バッチ管理者からCSV仕様、取込実装、対象テナントの承認一覧、既存設定との競合規則を入手する。文字コード、区切り・引用、ヘッダー、必須列、型、空値、重複、未知列、最大件数、設定キーの許可範囲を定義する。全設定スナップショットか部分更新かを判定し、前者はそのバッチ固有の正規形式へ変換、後者は許可パスだけを変更して兄弟フィールドを保存する。JSON契約移行の形式や格納先へ接続しない。テナントの認可はバッチに承認された範囲から与え、行の識別子と一致しなければ拒否する。形式・更新方式・対象キーが不明なら書込みを停止する。

5. **CSVの検証境界と書込み境界を分離する。** 将来の実装確認では、構造化パーサーで全入力を読み、全行を正規化・検証し、入力内重複と既存設定競合を解決してから書込み候補を確定する。既存更新は対象キーと期待旧値が明示承認された場合に限り、それ以外は競合として停止する。書込み時も対象テナントと検証時の状態を照合し、途中失敗を含めバッチ全体を原子的に反映できることを実装・隔離試験で示す。検証後競合や権限変更なら反映せず再検証へ戻る。単一トランザクション以外の方式でも部分公開を防ぐ保証が示せなければ本番書込みを許可しない。許可された読取りや候補の解析までを禁止する必要はない。

6. **別々に試験し、別々に承認する。** 参考例は変換範囲と全件検証の設計を点検するときに読む。将来の隔離環境ではJSONの既存・新規設定の互換性と復旧、CSVの正常系と異常行・他テナント・既存競合・途中失敗・再送・並行更新を、それぞれ実際の出力境界で試験する。テナント別・設定キー別の適用前後差分を期待値と照合し、ログには行番号と理由を残す。未達の経路だけを停止して原因と仕様を見直す。修正後は影響する試験を再実施し、両方をリリース対象とするなら両審査票の承認が揃って終了する。

## 完成条件

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. JSON経路：現行・新規設定と利用側の版の組合せについて、期待する読取り結果または明示的拒否が全件一致し、変換対象外の値が不変であること。移行件数・差分が承認範囲と一致し、復旧リハーサルで旧版の読取りが回復すること。不一致・未測定なら移行承認を停止する。
3. CSV経路：承認された有効行だけが対象テナント・設定キーへ反映されること。不正な後続行、対象外テナント、重複、未承認の既存設定競合、途中失敗の各試験ではバッチの永続変更が0件で、既存値と他テナントの値が不変であること。不一致なら書込み経路を停止する。
4. CSV経路：検証後の競合を検出して上書きを拒否でき、再送時に重複や意図しない更新を生じないこと。対象別の実測差分と承認差分が一致した場合だけ完了とし、件数だけの一致では合格にしない。
5. 文書完成：両経路それぞれに資料の入手先、開始前提、停止位置、期待差分、復旧担当と承認者を記録する。環境固有の未確定値は実行前の解決事項として残し、片方の合格を他方の合格に代用しない。
