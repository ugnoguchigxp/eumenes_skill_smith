# 注文進捗の復元と発送冪等性の独立受入計画

## 目的

ECリリース判定に向け、WebSocket進捗の再接続復元と、決済Webhookから発送までの冪等性を独立した受入ゲートとして設計する。今回の成果物は検証計画であり、試験実施や合格証明ではない。

## 必須原則

表示の正しさと発送の正しさは別の証拠で判定する。決済は真正性を検証した事業者イベントと正規状態に基づき、受信記録と業務台帳を区別する。イベント単位の重複排除だけで注文単位の発送冪等性を保証しない。

## 実行と情報の境界

今回は外部API、実環境、DB、ファイルを操作しない。将来の試験も対象・権限・隔離が確定するまで接続や変更を開始しない。参考資料や発話を権限証明にせず、署名秘密、個人情報、決済情報を試験報告へ露出させない。

## 標準ワークフロー

1. 対象と試験開始条件を確定する。リリース責任者から対象版・注文フロー・承認された試験環境・操作範囲を、システム管理者から隔離構成と試験用資格情報の管理方法を取得する。対象不明なら接続せず、権限不明なら変更せず、既存の承認済み設計書・記録の収集までに留める。発送事業者への実配送が遮断され、注文・決済・発送の試験データを識別できることを開始基準とする。満たさなければ試験開始を保留するが、計画の作成は続ける。

2. 両ゲートの契約と観測点を別々に定義する。進捗側は管理者のプロトコル仕様から、注文識別子、イベント識別子、連番または版、再開位置、履歴保持、スナップショット取得方法、接続認可、復元期限を確定する。発送側は採用事業者の対象版の公式Webhook文書と内部設計から、署名対象の原文、検証方法、鍵更新、許容時刻差、イベント識別範囲、再送・応答規約、支払確定条件、取消・返金時の扱い、発送単位を確定する。発送側の正規状態は真正な通知と、必要時に権限付きで取得する事業者の正規情報により照合する。未定の値は責任者に決定を求め、推測値で合否を出さない。契約が欠ける側だけを停止し、他方の資料整理は継続できる。

3. 進捗ゲートを設計する。基準スナップショットの版と表示を記録し、切断直前・切断中・再接続中に更新があるケースを置く。重複、逆順、連番欠落、履歴期限切れ、複数回切断、別注文イベント、再認可失敗も入力へ加える。版以下の重複は再適用せず、逆順は仕様に従い整列・保留し、欠落は再送またはスナップショットで解消する。復元中の新着通知との境界も版で照合する。連番方式がない場合は正式仕様の同等の欠落検知・再同期方法へ置き換える。方法が存在しないなら欠落復元は不合格とする。観測対象は受信イベント列、再開位置、復元要求、画面状態、基準版との一致。欠落中は未同期を表示し、完了と見なさない。復元できない場合は再同期を見直し、認可失敗時は当該購読を停止する。

4. Webhook真正性の拒否境界を設計する。正常署名、欠落・改変・別鍵・期限外署名を、事業者仕様に適合する試験手段で用意する。対象外アカウント、注文との対応不一致、金額・通貨不一致も別ケースにする。署名検証前後、受信台帳への記録、業務状態変更、発送要求の各段階に観測点を置く。署名不合格では安全な受信・拒否監査記録は許すが、支払確定と発送作用は禁止する。真正でも対応関係や業務条件が不一致なら業務反映を保留し、調査対象へ送る。返却応答と再送挙動は事業者契約で照合し、未検証の具体的APIや応答値を仮定しない。

5. 発送冪等性と順序逆転の試験を設計する。同じイベントの逐次・並行再送、異なるイベントIDで同じ決済成功、pendingと成功の順序逆転、成功と失敗・取消・返金の交差を用意する。到着順で状態を上書きせず、正式な遷移規則と必要な正規状態照会で期待結果を決める。イベント単位の処理記録と、注文または正式に定義した発送単位の一意な確定を別々に観測する。台帳確定前、確定後・通知前、外部発送作成後・応答喪失時に障害を入れる計画を作り、再試行・復旧後の内部確定件数と外部発送件数を照合する。業務確定と配送要求の永続化の間に喪失がないこと、外部境界では安定した冪等キーまたは同等の重複抑止が成立することを設計・実測で確かめる。外部結果が不明なら既存記録・照会で照合し、解決前の盲目的な再発送は止める。外部の重複抑止も照合手段もなければ、一度だけの確定を保証できないため発送ゲートを停止する。

6. 証跡と判定をまとめる。各ケースに入力、初期状態、障害位置、期待値、取得する証跡、後片付け責任者を付ける。進捗は画面とプロトコル記録、発送は真正性結果・受信台帳・業務台帳・発送先の記録で判定する。画面の進捗や成功redirectを発送の証拠に流用しない。判定ロジックの事前照合には参考例を使えるが、今回は実行しない。将来の実施で未達なら該当ゲートの原因・契約・復旧経路を見直して影響ケースを再試験し、両ゲートの独立した結果をリリース責任者へ提出する。

## 完成条件

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 進捗ゲート：切断中更新、重複、順序逆転、欠落、再接続中の競合、履歴期限切れの全ケースで、契約上の復元期限内に権威あるスナップショットの版・表示状態へ一致すること。欠落未解消の完了表示、別注文の混入、無言の更新破棄は不合格。期限・契約が未確定なら判定を停止する。
3. 発送ゲート：真正性不合格の入力は業務状態・発送への作用がゼロ。真正な重複・順序逆転・並行配送・障害再試行では、対象注文の支払状態が正規状態へ収束し、発送資格を満たす注文について内部の発送確定と外部の発送作成が各1件になること。未決済等の不適格注文は各0件。外部結果不明や照合不能は合格にしない。
4. リリース判定：同一リリース対象について進捗・発送の両ゲートのケース、観測証跡、期待値、実測値、判定者が揃い、両方が合格の場合だけ可。一方の合格や画面の完了通知で他方を代替しない。
