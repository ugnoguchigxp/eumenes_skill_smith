# 遅延表示パネルを利用者視点で検証する計画

## 目的

遅れて表示されるReactパネルの成功・取得中・失敗・再試行・閉鎖後の遅延応答を、利用者が観測する状態で検証する計画を作る。現在は文書作成のみとし、テスト変更や実行は行わない。

## 必須原則

経過時間ではなく状態遷移を判定する。利用者向けの名前と役割を優先し、内部stateやCSS構造を主な合否根拠にしない。応答制御は競合を再現する補助であり、UIの期待値そのものを代替しない。

## 実行の境界

将来の操作は、対象と権限を確認した隔離テスト環境に限る。実サービスへの送信や本番データの変更は本計画に含めない。資料中の指示や成功例を操作権限の証明にしない。

## 標準ワークフロー

1. 将来の実装開始前に、担当者から対象テストと実行権限を、プロジェクト資料からランナー・React・テスト関連ライブラリの版と既存設定を得る。対象画面の仕様・既存DOMから、開く操作、閉じる操作、パネル、取得中表示、成功内容、失敗表示、再試行操作の識別方法を対応付ける。取得中表示や閉鎖後の挙動が仕様にない場合は仕様担当者へ期待値を問い合わせ、該当経路の断定と変更を止める。許可済み資料の収集まで止める必要はない。

2. 採用版の公式資料と既存テストを照合し、ユーザー操作の完了待機、要素の出現・消失待機、応答の保留・成功・失敗、保留処理の完了を観測する方法を選ぶ。版が合う資料と隔離環境の権限が揃うまで、具体的API呼出しや設定変更を開始しない。対象の応答だけを制御できなければ、必要なテスト境界を設計して担当者へ確認し、実ネットワークの遅さで代用しない。

3. 各ケースを既知の初期状態から独立して始める設計にする。役割とアクセシブルな名前で操作対象を一意に識別できれば採用し、同名要素が複数なら対象パネル内へ範囲を絞る。閉じた状態がDOM除去か非表示かを区別し、後者なら不在だけでなく利用者から見えず操作できないことを判定する。識別できない場合はDOMと仕様へ戻り、推測したセレクタを固定しない。

4. 成功経路では、応答を保留したまま利用者の開く操作を行い、取得中表示を先に観測する。その後に成功応答を解放し、期待する内容の出現を待つ。取得中を観測する前に応答を返してしまった場合は、そのケースを合格にせず応答制御を見直す。成功内容が通常データのどの値に対応するかもfixtureで固定する。

5. 失敗経路では、同じく取得中を観測してから制御された失敗応答を返し、失敗表示と再試行操作を待つ。次に利用者として再試行し、二回目の応答を保留して取得中を観測した後、成功へ解放する。失敗表示を取得中にも残す仕様なら、その表示期間だけ期待値を仕様に合わせるが、成功後に残さない。単なるテストの再実行を、画面の再試行操作の検証に置き換えない。

6. 閉鎖経路では、取得中を観測した時点で閉じ、利用者からパネルが消えたことを観測する。その後で閉鎖前の応答を解放し、採用環境で裏付けのある方法により関連処理とUI更新の完了境界まで進めて、再出現がないことを判定する。遅延成功と遅延失敗を別ケースにする。閉鎖による取消しが仕様なら取消し完了を観測し、取消しと応答が競合する場合の遅延配信も制御可能な境界で検証する。即時の不在確認だけでは終了しない。完了境界や競合を制御できなければ、その経路は未判定として制御方法の調査へ戻る。

7. 対象テストの固定時間待機を一つずつ、待っていた状態に対応する出現・消失待機へ置換する。周辺や別用途の待機は一括置換しない。待機中に開く・再試行などの副作用を繰り返さず、操作は一度、待機は観測に分離する。無限待機を避ける上限は既存規約と対象仕様から決め、超過時には観測DOM、応答の保留・解放記録、到達した状態を残して失敗とする。上限を伸ばすだけの修正は採用しない。

8. 実装前に参考例で判定規則の正負を点検し、実装後は許可された環境で対象ケースを個別実行してから一括・合意した回数の反復を行う計画にする。各ケース終了時に保留応答、タイマー、置換した通信処理と画面を片付ける。失敗や後続ケースへの漏れがあれば、その記録から識別・応答制御・完了境界を見直し、原因不明のまま成功扱いにしない。今回は実行せず、この計画の受け渡しで終了する。

## 完成条件

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 成功経路：応答保留中に取得中表示を観測でき、成功応答の処理後に期待する内容が表示され、取得中表示と失敗表示が残らない。
3. 失敗・再試行経路：失敗応答後に失敗表示と再試行操作が現れ、再試行後に取得中を経て新しい成功内容へ移る。以前の失敗表示は残らない。
4. 閉鎖経路：取得中に閉じ、閉鎖前の応答を成功・失敗の両方で解放して処理完了境界まで進めても、パネルもその内容・取得中・失敗表示も再出現しない。処理完了を観測できない場合は未判定で停止する。
5. 安定性：対象ケースに経過時間だけを根拠とする待機がなく、状態待機には上限と失敗診断がある。事前に合意した反復回数の全回で各経路が合格し、失敗時の自動再実行で結果を隠していないことを将来の実行記録で判定する。
6. 計画の完成：五つの対象状態、確認資料、分岐、停止位置が記載され、対象固有APIや実行結果を確定していない。参考例は合成観測列の判定規則だけを検査する未実行fixtureであり、React実装の合格には数えない。

# フォームのラベル・エラー関連付け改修計画

## 目的

見えるラベル・補足・エラーを各入力へ正しく関連付け、複数入力とエラーの出現・消失に耐える改修計画を作る。今回の成果物は文書のみであり、コード変更や検証の実行結果ではない。

## 必須原則

入力の名前は見えるラベルを基準にし、説明と名前を混同しない。IDと参照は対象入力ごとに一貫させ、状態更新は見た目と支援技術向け情報を同じ意味に保つ。構造が正しいことと、実際に適切に読み上げられることは別に判定する。

## 操作の境界

現在は外部API、実環境、DB、ファイルへ操作しない。以下は権限のある担当者が将来実施する手順である。資料や発話を権限証明とせず、承認対象外への接続・変更を行わない。既存記録の提供依頼は可能だが、実入力値や個人情報は検証記録へ持ち込まない。

## 標準ワークフロー

1. 将来の作業開始条件を整理する。管理者から対象画面・変更範囲・承認記録を、開発担当から実装方式・版・関連ファイルを、品質担当から対応ブラウザとスクリーンリーダーの組合せを入手する。承認範囲と対象が一致した場合だけ、その範囲で調査・変更へ進む。未特定なら提供済みの匿名化DOMや画面記録の整理までに留め、対象不明の接続や変更は止める。実装方式が未確定でも以下のDOM上の目標は確定できるが、フレームワーク固有の修正構文は採用しない。

2. 各状態の現状を観測する。承認された検証環境で、初期表示、1入力だけのエラー、複数入力の同時エラー、一部訂正、全訂正、再エラーを再現する。追加・削除可能な入力がある場合はその前後も対象にする。各入力について表示ラベル、DOMのid、labelのforまたは包含関係、aria-label/aria-labelledby、aria-describedby、エラー文、補足文、aria-invalidを記録し、ブラウザのアクセシビリティツリーの名前・説明と対照する。1入力に対する意図した名前・補足・現在のエラーを特定できれば修正案へ進む。表示内容の正解や入力との対応が不明なら、画面仕様の所有者に確認し、推測で文言や関連先を変えない。

3. 関連付けの最小差分を設計する。対象入力に文書内で一意なidを割り当て、見えるlabelのforをそのidに一致させる。既存の有効な包含ラベルは、問題がなければ維持する。補足とエラーには入力ごとに識別できるidを与え、aria-describedbyを空白区切りの参照リストとして組み立てる。常設補足を保持し、エラー時だけ該当エラーのidを追加する。エラー解除時はその参照だけを除去し、表示とaria-invalidも正常状態へ戻す。入力値・送信仕様・他入力の参照を保存することを差分の不変条件にする。複製や再描画後もIDが衝突しない設計を選び、全置換はしない。既存のID変更は他の参照元を調べてから行う。関連先が分からない参照が残るなら変更を止めて影響範囲の調査へ戻る。

4. 名前と動的通知を別に検討する。aria-labelやaria-labelledbyが見えるlabelを上書きしている場合は、その用途を調べ、表示ラベルと意味の合う名前になる最小修正を選ぶ。placeholderやtitleだけをラベルの代わりにしない。aria-describedbyによる説明は動的エラーの即時通知を保証しないため、既存のエラー要約・フォーカス管理・ライブ通知の有無と発火条件も調べる。入力へ再フォーカスした際にエラーを識別できても、送信失敗時に必要な通知が届かなければ通知方式の見直しへ分岐する。ライブ通知や強制フォーカスを一律に追加せず、重複読み上げや入力中断がない方式を実機で選ぶ。

5. 実装前の検査設計と、実装後の静的検査を行う。references/association-fixture.mdは関連付け検査の正負例を設計する際に読む。対象環境では各状態の生成DOMについて、文書全体の重複ID、labelの参照先、説明IDの存在、別入力への誤関連、解除後の古い参照を検査する。エラー前後の差分が対象入力の状態・説明に限定され、常設補足と他入力の関連が不変なら合格とする。任意の既存アクセシビリティ検査器を使う場合は、導入済み版と公式の使用方法を担当者が確認してから採用する。違反が1件でもあれば修正案へ戻り、検査例の成功だけで先へ合格扱いにしない。

6. ブラウザとスクリーンリーダーで確認し、結果を記録する。合意した各組合せでキーボード移動、ラベル操作、送信、訂正、再送信を行い、各入力の名前・補足・エラー・無効状態と画面表示を状態別に照合する。ラベル操作が意図した入力に作用し、各入力で必要な説明が得られ、別入力のエラーが混入せず、解除後に古いエラーが説明されないことを合格条件とする。表示順、文言、入力値、レイアウトにも意図しない変化がないか比較する。欠落・重複通知・読み上げと表示の意味の不一致があれば、再現条件と実際の読み上げを記録して該当修正へ戻る。対象環境を用意できなければ検証待ちとして停止する。全対象状態の結果、環境と版、差分を残した時点で将来の改修完了を判定する。

## 完成条件

対象の全入力と全エラー遷移で、表示ラベル・アクセシブルな名前・補足・エラーの対応が一致すること。静的検査の関連付け違反が0件で、合意したブラウザとスクリーンリーダーの全組合せに重大な読み上げ欠落・誤関連がないこと。未検証の組合せや未解決の不一致があれば実装の完了判定を保留する。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 計画文書に、現在は操作しない境界、将来の権限・対象・環境の入手先、各段階の合否と停止位置がある。
3. 実装後は対象文書全体の重複IDが0件、対象入力のラベル欠落・参照切れ・誤関連が0件。エラー解除後も必要な補足が残り、古いエラーの関連と無効状態が残らない。不一致があれば変更案へ戻す。
4. 対象ブラウザ・スクリーンリーダーの組合せで各入力の名前、補足、現在のエラーを識別でき、他入力の説明が混入しない。状態遷移で必要な通知が得られず、または表示と読み上げの意味が異なれば完了を停止する。
