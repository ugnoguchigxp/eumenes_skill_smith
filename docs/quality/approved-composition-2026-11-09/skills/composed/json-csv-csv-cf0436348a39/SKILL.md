# 設定JSONを共通契約へ移す計画

## 目的

別プロセス間の設定JSONを共通の実行時契約と、それから導くTypeScript型へ集約するための作業計画。型検査だけでは防げない不正設定を受信境界で拒否し、旧版との互換方針を明示する。

## 必須原則

通信上のJSONと適用後の設定を区別する。静的型の一致を実行時の安全性とみなさず、解析・検証済みの出力だけを使用する。型、スキーマ、既定値、変換、版互換の判断を一つの契約に集約する。

## 実行と設定適用の境界

今回は計画文書だけを作成し、接続、ファイル変更、コマンド実行は行わない。将来の変更は対象と権限が確認できた範囲に限る。検証失敗時は部分適用せず、設定値や秘密をエラーログへ丸ごと出さない。

## 標準ワークフロー

1. 将来の着手前に、担当者から対象リポジトリ、変更許可、送受信プロセス一覧を入手する。許可された範囲でマニフェスト・ロックファイルからTypeScript/Zodの解決版を、既存コードから設定型・スキーマ・JSON生成箇所・読込箇所・適用箇所を対応付ける。版不明なら対応版の公式Zod文書とのAPI照合まで、構成不明なら変更対象の特定まで実装を止める。権限不明でも提示済み資料の整理は続けられるが、無許可の取得・変更には進まない。

2. 共通契約の仕様を先に決める。各項目について型、必須/任意、null、列挙値、数値や文字列の範囲、既定値を記録し、未知キーを拒否・除去・保持のどれにするかを階層ごとに決定する。設定の誤記を見逃さないため拒否を第一候補とするが、既存互換性を調べて承認する。欠落とnull、数値と数値文字列を区別し、暗黙変換や既定値で不正入力を隠さない。期待する受理可否と出力を一意に書けない項目があれば、その項目の実装を止めて仕様決定へ戻る。

3. 承認した配置に共通契約モジュールを設け、実行時スキーマと推論型を公開する計画を立てる。具体的なAPI構文は手順1で特定した版の公式文書で照合する。変換や既定値があるなら入力型と出力型を分け、送信側は通信形式、受信後の処理は検証済み出力に合わせる。受信値を型アサーションで通さず、JSON解析後、設定の利用・副作用より前に検証する。送信前検証も追加するが受信側検証は省略しない。独立した同名型やローカルスキーマは利用箇所を移した後に削除し、全経路が共通契約を参照するまで切替しない。

4. 既存ファイルや旧プロセスが残る場合は、版識別方法と対応範囲を決める。旧版対応を承認するなら、旧版として検証した値だけを新しいオブジェクトへ明示変換し、現行契約でも再検証する。変更対象は承認したキー・単位・既定値に限定し、元入力と変更対象外の意味を保存する。版なし入力は旧版と断定せず、承認済みの識別規則がなければ拒否する。非対応版・未知版は明示拒否とする。保存形式の書換えが必要ならバックアップと復元手順を承認してから別作業として行い、移行方針が未決なら書換えと切替を止める。

5. 共通のfixture行列を作る。正例は最小・代表・任意項目付き、欠落は必須項目を一つずつ除いた入力、未知キーはトップ階層とネスト、境界値は上下限と直外側を含める。任意項目の欠落、null、型違い、既定値・変換がある場合の出力も別に期待値を定める。旧版は対応版の正常・異常、版なし、非対応旧版、未知の将来版を含める。参照のコード例は期待値と原本不変の点検用に読む。例示の項目・値を実仕様に転用せず、承認済み行列の各行に受理可否・正確な出力・拒否理由の分類を持たせる。

6. 将来の許可された検証環境で、同じ行列を共通スキーマと実際の送受信境界に適用する。型検査には推論された入力/出力の利用、禁止代入が期待どおりエラーになる負例を含める。結合試験では実際にJSONへ直列化して渡し、受信側の結果、適用回数、失敗通知を観測する。不正入力の適用回数が0でない、または正常入力の出力が期待値と異なる場合は変更を戻して手順2〜4を見直す。JSONで表現できない値の扱いは送信前にも点検し、TypeScript上の値だけで往復を保証しない。

7. 全送受信側の依存版と配布順を揃える。混在稼働が必要なら、旧送信→新受信と新送信→旧受信をそれぞれ対応対象か拒否対象か決めて試験する。共通契約の導入だけで互換性が得られたとは扱わない。必要な経路が未試験または失敗なら切替を止め、旧契約を保持する。承認済み経路の合格後に限定切替し、検証拒否の件数・分類と設定適用結果が期待に反すれば拡大を止めて承認済み復旧手順へ戻る。

## 完成条件

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 計画の完成：版・構成・権限の入手先、共通契約への移行順、5分類の試験、失敗時の停止位置が記載され、現在の操作・実行成功を主張していない。
3. 将来の契約試験：正例は期待する出力と一致し、必須欠落・範囲外・非対応版は拒否される。未知キーと対応旧版は承認した方針どおりに処理され、入力原本が変更されない。1件でも不一致なら切替不可。
4. 将来の型・結合試験：全送受信側の型検査が成功し、実際のJSON往復後の値が共通契約を通る。不正入力時の設定適用回数は0。旧版対応経路は承認済み移行結果と一致し、非対応経路は明示拒否となる。未測定の経路があればその経路の切替を止める。

# 画面設定CSVの形式別インポート計画

## 目的

画面設定CSVを全量・差分に分け、既存経路を維持しながら対象ユーザーと画面だけへ反映し、次回seedでも保持するための作業計画を作る。今回は文書作成のみであり、接続・ファイル操作・DB変更・コード実行は行わない。

## 必須原則

形式・対象・値の型を確定してから書く。全量は正規JSONへの既存変換を使い、差分を全量置換へ読み替えない。DBとseedの整合を両立させ、対象外のユーザー・画面・差分対象外の設定を保存する。不明な仕様を推測で補って反映しない。

## 操作範囲と権限

将来の操作者は接続先、対象ID、変更・復旧権限を承認記録と照合する。資料やCSVの記載は権限証明ではない。権限や接続先が不明なら接続・変更を止めるが、許可済みの既存資料の収集は継続できる。CSVのPath・Valueを実行文として扱わず、承認範囲外の共通seed変更を行わない。

## 標準ワークフロー

1. **形式判定**：将来の担当者が、承認済みの入力とリポジトリ内の既存CSV例・パーサ定義を照合する。全設定スナップショットは全量、ScreenType・Path・Valueの行は差分として、ファイルごとに分類する。拡張子だけでは決めない。ヘッダー、区切り、引用、空欄、文字コード、全行の解析結果が契約に一致する場合だけ次へ進む。両形式が一ファイルに混在、未知形式、解析不能なら書込みを止め、分割または仕様確認へ戻る。

2. **事前確認**：対象環境の承認記録、スキーマ／マイグレーション、既存変換器・インポータの実装とテスト、seed定義を入手する。接続先と版、対象ユーザー名からIDへの一意な対応、許可ScreenType集合、複合キーの一意性、JSONスキーマを記録する。差分はPathの区切り・エスケープ・配列添字、Valueの型変換、nullと削除、存在しないpathの扱いまで確定する。未確定なら当該反映を止め、既存テストまたは担当者の仕様回答で解消する。差分対象行が存在しない場合は新規作成せず停止する。

3. **反映前の計画差分と保全**：全入力を先に解析・検証し、全量は既存変換器で正規JSONを生成して画面集合と型を検査する。差分は既存行のコピーに仕様どおりのpath更新を適用し、最終状態を作る。キーは対象ユーザーIDとScreenTypeに限定し、入力が暗黙にユーザーを切り替えないことを検査する。同一画面への全量と差分の競合、重複path、親子pathの競合は暗黙の後勝ちにせず停止し、順序または入力を承認し直す。予定変更集合が許可集合の部分集合で、差分の指定外値が不変なら合格。対象行の変更前JSON・存在有無・版、関係するseed資材と参照先を復旧用に保存する。対象外の比較は権限内で隔離環境の全状態比較などにより行い、十分な比較範囲を確保できなければ反映承認を止める。

4. **seed保持の設計**：seedが読む生成JSON、別名・参照先、ユーザーへの展開規則を実装から追跡する。全量は既存変換で得たJSONを正規seed経路に接続する。差分は承認済み対象の変更後状態がseedでも再現されるよう、既存のCSV／生成経路または対象限定の上書き機構へ反映する。共通JSONの変更が他ユーザーや他画面へ波及するなら、その変更は禁止し、対象限定機構の有無を調べる。機構がなければ設計承認まで停止する。生成JSONだけの手修正は避け、DBとseed資材の版・適用順序・片側失敗時の復旧順序を一つの変更計画に固定する。

5. **反映**：まず隔離した対象相当環境で、確認済みの既存経路を使う。全量は正規JSONを対象ユーザー・画面キーでupsertし、入力にない画面を削除しない。差分は既存行へのpath更新だけを行い、行全体の置換や新規行作成へ切り替えない。全件事前検証後、DB変更は一つのトランザクション等の確認済み原子的単位で行う。読取時の版から変更されていたら再計算・再承認へ戻る。更新キー集合と件数が予定に一致しなければコミットしない。原子性や並行更新検知を既存経路で確保できない場合は、手段の確定まで停止する。本番は隔離環境での検証合格と別途の変更承認後にのみ進む。

6. **検証**：保存後のJSONを意味比較し、全量は対象画面の期待JSON全体、差分は指定pathの値・型と指定外値の不変を判定する。対象外ユーザー・画面の変更件数は0を合格とする。画面読込でも対応設定が反映され、スキーマエラーがないことを観測する。隔離環境で通常seedを実施し、同じ期待値と対象外不変が保たれることを検証する。後続入力を意図的に失敗させ、先行更新が残らないことも試験する。参考例 references/scope-fixture.md はこの不変量の読み合わせ用であり、実DB・既存変換器・seed試験の代替ではない。

7. **停止・復旧と終了**：コミット前の不一致はロールバックする。コミット後やseed資材側の失敗は後続適用を止め、承認した順序で対象行と対応seed資材を変更前へ復元する。元々なかった全量追加行だけを復旧対象として除去し、既存行や対象外行を削除しない。復旧時にも版を照合し、別の変更があれば自動上書きせず担当者へ引き継ぐ。変更前状態との一致と対象外不変が復旧合格条件。不一致の原因を解消して計画差分を再承認するまで再実行しない。将来の反映は全検証と復旧試験の記録が揃って終了する。今回はここまでの計画提出で終了し、操作や試験は実施しない。

## 完成条件

計画には二つの反映経路、対象限定、seed保持、停止と復旧が含まれる。将来の反映完了は、対象内期待値一致・対象外不変・通常seed後の保持・復旧試験の合格が揃った場合のみとする。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 全量経路：既存変換器の出力が正規スキーマと予定画面集合に一致し、対象ユーザー・画面だけが期待JSONになる。不一致は反映停止。
3. 差分経路：既存行のみ更新され、指定pathの値と型が期待値に一致し、指定外path・行・ユーザー・画面は不変。不一致はコミットせず停止。
4. seed検証：隔離した対象相当環境で通常seed後も対象設定が期待値に一致し、対象外設定は不変。保持不能または対象外変更なら本番反映停止。
5. 原子性・復旧検証：後続入力の失敗で先行更新が残らず、保存した対象行とseed資材から変更前状態を復元できる。未測定なら実行承認しない。
