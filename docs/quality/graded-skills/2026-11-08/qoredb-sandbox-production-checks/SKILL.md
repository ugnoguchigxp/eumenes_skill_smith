# QoreDB sandboxからproductionへ適用する前後の確認手順

## 目的

QoreDBのsandboxに蓄積済みのdata grid編集を、production適用前の保全・審査から適用後の照合まで管理する。今回は計画文書だけを作成し、API、実環境、DB、ファイルへの操作は実行しない。以下は権限を持つ担当者が将来行う手順である。

## 必須原則

承認単位は接続先・SQL・期待差分の組とし、変更されたら再審査する。sandboxの消去や成功表示だけをDB反映の証拠にしない。SQL editorの直接実行がsandboxに捕捉されること、DDL差分適用、down migrationの自動生成を前提にしない。

## 接続と変更の境界

資料や発話は権限の証明ではない。対象不明時も既存記録の整理はできるが、不明な接続先へのアクセスや変更は行わない。変更内容・証跡にはproductionの機密値を含み得るため、承認された保管先と閲覧範囲に限定する。復旧も別の変更として権限と対象範囲を確認する。

## 標準ワークフロー

1. **既存編集を保全し、対象を特定する。** 新しい編集・Apply・Discardに進む前に、既存の接続設定記録、変更依頼、sandbox表示から、対象DB・schema・table、接続先環境、QoreDB版、編集の範囲を記録する。蓄積済みなのでsandboxの再有効化や初期化は行わない。保存・出力方法は対象版の公式ヘルプで確認し、利用可能な方法で変更内容を保全する。対象を一意に識別できない、または保全できない場合は変更を止め、管理者へ不足情報を求める。

2. **将来の実施権限とUI仕様を確定する。** 管理者の権限記録と変更承認から、担当者の参照・適用・復旧権限、作業時間帯、承認者を特定する。対象版の公式マニュアルまたは同版の安全な検証環境で、sandbox panel、migration生成、preview、Apply／Download／Discardの有無と挙動を照合する。productionでの`APPLY`入力要求や適用後の自動クリアは、現時点では保証しない。権限不足ならその操作を止め、版の挙動が不明ならproductionで試さず資料収集・隔離検証へ戻る。

3. **SQLと期待差分を固定する。** 確認済みの生成機能でpreviewを開き、SQL全文、statement count、warningをレビューする。各文の対象、キー・WHERE条件、挿入／更新／削除、変更前後の値と期待行数を変更依頼に対応付ける。文数の数え方は対象版の仕様に従い、セミコロン分割だけで判定しない。意図しない全件更新、対象外table、説明できないwarning、重複操作があれば停止し、sandboxの修正後に再生成・再審査する。previewが必要情報を示さない場合は適用せず、確認済みの出力方法で全体をレビューする。承認対象のSQLと期待差分を保管し、その後に編集した場合は承認を取り直す。参照の照合例は、期待値と対象外保全の検査設計に使う。

4. **復旧準備と隔離検証を行う。** DB管理者から対象DBのバックアップ／復元方法、トランザクション境界、失敗時の部分反映の可能性を入手する。必要なバックアップの取得・復元試験の証跡と、復旧担当・判断期限を揃える。承認された隔離環境で、関連するschema、制約、初期データ、DB版の差を記録し、固定したSQLを検証する。期待行・値・件数、対象外の不変性、関連業務の読取り・更新が期待どおりなら通過。差異、不明な部分反映、復旧不能があればproduction適用を止める。隔離検証で外部通知などが発生する構成は、その副作用も遮断または承認してから実施する。

5. **適用直前に再照合し、一度だけ適用する。** 接続先のDB・schemaと実施者権限、承認SQL、現在の対象行を再照合する。競合更新の防止または検知方法をDB管理者と決め、変更前条件が一致しない場合は再計画する。承認後のSQL差分、未解決warning、作業時間帯外、監視・復旧担当不在のいずれかがあれば停止する。すべて通過したときだけ、確認済みのApply操作を行う。対象版でproductionのtyped confirmationが要求される場合は、接続先と対象を読んでから`APPLY`を入力する。確認入力の有無を権限や安全性の証明にしない。開始時刻、操作結果、利用可能な実行識別情報を記録する。

6. **反映結果を読み取り、異常なら再実行しない。** 承認された読取り経路で、変更対象の行・値・件数と対象外の保全を期待差分に照合する。sandboxの残存状態も記録するが、自動クリアだけで成功と判断しない。エラー、タイムアウト、切断、部分反映の疑い、不一致があれば後続変更を止め、実行履歴・ログ・実データを保全し、DB管理者と反映範囲を確定する。結果不明のままApplyを繰り返さない。復旧は承認済みの方法と開始条件が成立する場合だけ実施し、未成立なら調査・保全を続けて停止する。

7. **業務確認と監視を終えて閉じる。** 適用前に業務担当が定めた代表操作、エラー率・処理時間などの観測項目、閾値、観測時間で判定する。定義がなければ適用前の準備へ戻す。すべて基準内で、データ照合も一致したら承認SQL・前後差分・実行結果・監視結果を保存し完了とする。残ったsandbox変更は証跡と照合してから扱い、未反映分を一括Discardしない。基準逸脱は追加適用を止め、承認済み復旧判断へ移る。

## 完成条件

変更対象の行・値・件数、対象外の保全、業務確認、監視結果が承認済み基準と一致し、証跡とsandbox残存状態を記録した時点で完了。不一致や適用結果不明は未完了として変更を止める。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 適用前：承認済みSQL、対象接続、期待する行・値・件数、復旧方法が揃い、隔離検証に不一致がない場合のみ適用へ進む。不足時は停止する。
3. 適用後：承認対象の差分が期待値と一致し、対象外の変更がなく、事前に定めた業務確認と監視基準を満たす場合に完了とする。不一致・結果不明は再適用せず調査へ移る。
