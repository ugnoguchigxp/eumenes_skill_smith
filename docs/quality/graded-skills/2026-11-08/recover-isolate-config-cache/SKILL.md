# 設定混入の復旧と文脈別キャッシュ分離計画

## 目的

同じconfigPathで二つのプロジェクトを開くと設定が混ざり、pluginPathsも異なる事象について、正しさ優先で復旧し、その後に原因を絞って恒久対応する計画を作る。今回の成果物は文書のみであり、復旧・変更・実測はまだ行わない。

## 必須原則

キャッシュ衝突は有力な仮説であり、確定原因とはしない。設定結果に影響する文脈を共有しないことを判断軸とし、速度より設定の一致を優先する。pluginPathsの順序・重複・パスの意味を、仕様上の根拠なく変えない。

## 操作と情報の境界

現在は外部API、実環境、DB、ファイルを操作しない。以下の操作は将来、対象管理者の許可と対象範囲の確定後に行う。資料や発話だけを権限証明にしない。設定原本の削除や共有キャッシュの一括消去は復旧の既定手段にせず、既存記録の収集と変更操作を分ける。

## 標準ワークフロー

1. **対象と開始条件をそろえる。** 将来の担当者は、管理者の承認記録と対象一覧を照合し、製品名・版、二つのworkspaceRoot、configPathの実際の解決先、順序付きpluginPaths、プロセス構成を記録する。版や設定機構は対象版の公式資料・実装から、権限は組織の承認経路から得る。対象不明なら新規接続を止め、許可範囲内の既存ログ・構成記録だけを集める。対象は分かるが変更権限がなければ、読取り範囲の調査までとし、再起動・無効化・消去へ進まない。
2. **保全し、復旧の比較基準を作る。** 許可後、未保存作業、原設定、関連ログ、起動順を保全する。各プロジェクトの正しい有効設定とプラグイン解決先を、承認済み構成と隔離した単独起動結果から照合する。両者が一致すれば期待値として記録し、混入検出用には既存の識別可能な差分を使う。一致しない、または保全できない場合は変更を止め、所有者と期待値を確定する。障害中の混合結果を正解にしない。
3. **まず復旧する。** 対象版の公式資料または実装で設定キャッシュを無効化する方法と影響範囲が確認できた場合、その範囲だけ無効化し、必要な再起動・再読込を承認の上で行う。方法が不明なら引数を推測せず、共有状態を持たないことを確認した別プロセス、または一方ずつの利用を選ぶ。プロセスを分けるだけで永続キャッシュも分かれるとは仮定しない。各採用経路で手順2の期待値と完全一致し、他方の識別値がなければ限定的に利用を再開する。混入が残る場合は通常利用を停止して保全状態へ戻り、無差別なキャッシュ削除はしない。復旧が成立するまで恒久変更の展開を先行させない。
4. **復旧後に原因を絞る。** 隔離した検証環境で、キャッシュの生成元・読取り・書込み・無効化箇所とキー、プラグイン解決、可変オブジェクトの共有、並行更新を追う。同じconfigPathでpluginPathsやworkspaceRootが違う二つの文脈が同じエントリに到達するなら、キー不足を支持する証拠とする。無効化で症状が消えるだけでは原因確定としない。衝突が観測されなければキー変更を必須修正にせず、共有状態の調査に戻り、復旧構成を維持する。
5. **原因に対応した恒久変更を限定実装する。** キー不足が確認された場合、少なくともworkspaceRoot・configPath・順序付きpluginPathsを構造化してキーに含める。単純な文字列連結で境界を失わない。相対パスは対象実装が定める基準ディレクトリで解決するが、大文字小文字・symlink・順序・重複の同一視は公式仕様または実装上の同値性を確認できたものだけに限定する。対応不明なら正規化を見送り、同値性の調査へ戻る。設定やプラグイン変更後の無効化、旧キーの残存エントリを再利用しない切替、共有可変値の隔離も実際の依存関係に合わせる。他の結果依存要素が見つかればキーか寿命管理へ追加する。参照の最小検査例を設計レビューに使い、対象実装のテストを別途作る。
6. **回帰検証して段階展開する。** 同じconfigPath・異なるpluginPathsの二つで、A→B／B→Aの起動、交互・並行アクセス、片側の設定／pluginPaths変更と再読込を試し、毎回それぞれの期待値と照合する。単独起動、新旧エントリの切替、他方の設定が不変であることも試す。期待値との不一致が一つでもあれば展開を止め、変更を戻して手順3の合格済み構成を維持する。全条件が一致した場合のみ限定展開し、同じ観測項目で再発を監視する。性能調整はこの合格を維持できる範囲で最後に行う。

## 完成条件

復旧完了は、採用した利用形態で両プロジェクトの設定とプラグイン解決先が各期待値に一致すること。単独利用だけが合格なら、二つ同時の利用制限を残す。恒久対応完了は、二重起動と再読込を含む回帰試験がすべて一致し、失敗時に復旧構成へ戻せること。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 復旧：各プロジェクトの有効設定とプラグイン解決先が承認済みの単独時期待値に一致し、他方の識別値が出ない。不一致なら利用再開を停止する。
3. 恒久対応：同じconfigPath・異なるpluginPathsで、起動順の反転、交互アクセス、並行アクセス、片側の再読込後も双方が期待値に一致する。失敗時は展開せず復旧構成へ戻す。
4. 参照コード：旧キーの衝突を検出し、新キーでは異なる文脈とプラグイン順序を区別するassertが揃っている。未実行であり、対象製品の合格証拠にはしない。
