# workspace・plugin差分を混在させない汎用キャッシュ設計計画

## 目的

二つのworkspaceが同じ汎用cache APIを利用しても、同じconfigPathに由来する値へworkspace差分やplugin差分が混入しないキー設計と検証計画を作る。業務判断は呼出側に置き、リポジトリ層は汎用の保存・取得に限定する。今回の成果物は文書のみであり、実装・接続・ファイル操作は行わない。

## 必須原則

キャッシュキーは計算結果を決める実効入力の同一性を表す。workspaceRoot・configPath・pluginPathsを最低限の分離軸とし、文字列の単純連結は使わない。意味の異なる入力を正規化で同一化しない。キーの分離と内容更新による失効は別々に保証する。汎用cache層にはplugin選択や業務上の共有可否を判断させない。

## 実行と情報の境界

以下の操作はすべて将来の計画である。現在は外部API・実環境・DB・ファイルへ操作しない。将来の接続・読取り・変更は、それぞれ対象と権限が明示された範囲に限る。資料の記載や発話は権限証明としない。既存の提供済み資料は整理できるが、対象不明の接続や変更は行わない。診断記録には秘密を含む設定値ではなく、テスト用識別子とヒット／ミス・結果の対応を残す。

## 標準ワークフロー

1. 責務と実行前提を整理する。提供済みの呼出経路・型定義・設計資料から、業務判断を行う呼出側、キー生成アダプタ、汎用cacheリポジトリの境界を記述する。将来の調査では管理者から対象workspaceと読取り／変更権限を、対象版の公式資料・公開型定義・実装からcache APIのキー型、名前空間、シリアライズ、削除・失効仕様を得る。合格条件は、二つのworkspaceの識別方法とAPIへの格納表現が定まり、repositoryがworkspaceやpluginを選択しないこと。API契約不足なら既存資料の整理までに止め、未知の呼出しや接続を行わない。権限不足なら当該対象への読取り・変更を止める。

2. 実効入力の一覧を作る。呼出側でworkspaceRoot、configPath、pluginPathsを解決する位置を特定し、同じconfigPathでもworkspaceまたはpluginが違えば異なる計算になるかを仕様と呼出経路から判定する。相対configPathはどのworkspace基準か、pluginPathsは探索先か解決済みpluginか、ロード順に意味があるかを明記する。設定内容・plugin内容や版・環境など、結果へ影響する追加入力も列挙する。意味が未確定の項目が一つでもあれば、正規化・共有範囲の確定を止め、提供済み資料または権限内の観測へ戻る。

3. キー変換を設計する。呼出側のアダプタで、名前空間／キースキーマ版、workspace識別子、config識別子、順序付きplugin識別子列、更新を識別するrevisionを、型と境界が保たれる構造としてエンコードする。汎用APIが文字列キーなら衝突しない構造化エンコードを渡し、型付きキーなら同じ情報を保持する。パスの相対解決は手順2で定めた基準に限定する。大文字小文字の変換、symlink統合、plugin列のソート・重複除去は、対象環境で意味を保存すると証明できた場合だけ行う。入力の区別、plugin順序、要素境界を不変量とする。同一実効入力は同一キー、workspaceまたはplugin差分は別キーが合格条件。制限長などで表現できない場合はAPI契約へ戻り、黙って切り詰めない。

4. 更新と停止経路を決める。内容変更を検出できる版・ダイジェスト・世代番号のいずれかを対象仕様に基づいて選び、設定やplugin更新時にrevisionを変えるか、影響範囲だけを確実に失効させる。固定パスだけでは内容更新を区別できず、TTLだけでは更新直後の正しさを保証しない。旧形式のキーは新しい名前空間から読まない。更新検知や安全な失効が成立しなければ共有キャッシュの有効化を止める。無効化して通常計算へ戻す案は、APIが対応し権限がある場合だけ選び、対応不明なら操作せず設計を差し戻す。

5. キー設計をオフラインで検査する。将来の実装前にreferences/cache-key-fixture.mdを読み、同一条件の一致、workspace差分、plugin差分、順序差分、更新差分、単純連結の衝突を検査する。参照例は順序を保持するため、順序非依存と確定した設計では、その仕様と期待値の変更をレビューしてから使う。全assert成立・終了コード0でキー表現の検査を通過とし、失敗時は手順2〜4へ戻る。現在は実行せず、参照例の成功を実cache APIの成功として扱わない。

6. 権限のある隔離環境で結合検査する計画を作る。同じAPIの実契約に従い、同一configPathを使うworkspace A/Bに識別可能な別の期待結果を用意し、A→B→A、B→A→Bと交互・並行に呼ぶ。pluginだけを変えるケース、同一入力の再呼出し、設定／plugin更新後の再呼出しも加える。観測対象は返却結果、キーまたは非機密な識別子、再計算回数／ヒット・ミスで、相互混入ゼロ・差分時の分離・同一時の再利用・更新後の旧値返却ゼロを合格とする。APIにヒット情報がなければ承認された呼出側の計算回数で判定し、観測できなければ未測定として有効化を止める。不一致はキー入力・正規化・失効・共有状態のどこかを調査して再検査し、原因を決めつけた修正や無関係な全消去は行わない。

## 完成条件

同一configPathに対するworkspace差分・plugin差分の分離、同一条件での再利用、更新後の失効をそれぞれ判定できる計画になっていること。将来の有効化は結合検査の全条件成立後に限り、混入・失効漏れがあれば停止する。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 設計文書：workspace・config・pluginの識別、更新時の失効、責務境界、各停止位置が記載されていれば合格。欠落時は実装へ進まない。
3. 将来のオフライン検査：参照例の全assert成立と正常終了を合格とする。未実行は未測定、失敗時はキー設計を見直す。
4. 将来の結合検査：二つのworkspaceで相互の値が一度も返らず、plugin差分でも別値となり、同一条件では再利用でき、更新後に旧値を返さないこと。権限・API契約不足または一件でも不一致なら共有キャッシュの有効化を停止する。
