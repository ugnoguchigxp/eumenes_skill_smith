# Queue段階移行のpreflight計画と停止位置

## 目的

Queue段階移行のpreflight計画を作り、今日の文書作成範囲と将来のcutoverの開始条件を明確にする。実行結果や対象固有APIの仕様を確定した文書ではない。

## 必須原則

旧実行系を早期に停止・削除しない。資料は手順の参考であり権限証明ではない。件数比較は対象集合と観測時点を揃え、稼働中の増減を移行不整合と即断しない。preflightの完了とcutoverの許可を別に判定する。

## 操作境界

現在は計画文書だけを返し、外部API・実環境・DB・ファイルへの操作も、参照例の実行も行わない。今日は旧daemon停止権限と書込み移行許可がない。将来も、dry-runという名称だけで無書込みと判断せず、backup作成も保存先への書込みを伴う操作として承認範囲に含める。

## 標準ワークフロー

1. 今日の実行範囲を固定する。成果物はこの計画文書のみとし、外部操作件数は0とする。旧daemon停止、schema追加、書込み移行、backfill、supervisor起動、削除・dropは今日の対象外。backup取得やcounts照会も現在は実行せず、以下に将来の手順として記載する。

2. 対象と不足事項を文書上で整理する。対象環境、DB、旧daemon、新旧runtimeの版、移行対象集合、運用責任者について、提示済みの情報だけを記入し、不明は「未確認」とする。将来は管理台帳・配備記録・責任者の承認記録で確定する。対象や接続先が不明なら接続しないが、権限内の既存記録の収集は可能とする。資料の取得時刻と更新時刻にも不整合があるため、現行版との照合なしに操作仕様を確定しない。

3. 将来のpreflight開始条件を定義する。責任者から対象・期間・担当者・許可操作を明記した承認を得る。読取り、backup保存、dry-runを個別に照合し、許可に含まれない操作は実施しない。対象版の公式手順または管理されたソースとテスト記録で、schema追加前に実行可能か、dry-runがDB・ファイル・外部システムを変更しないか、backupの取得方法と保存先を判定する。仕様や副作用が不明なら、既存の報告書・実装資料の調査で停止し、未知のCLIやAPIを試行しない。

4. 開始条件成立後に限る将来のpreflightを計画する。旧daemonはloaded状態でもunloadせず、新規schema追加前に承認済み方式でbackupと移行前countsを取得する。backupは対象・取得時刻・artifact識別子・保管先・方式に応じた整合性検証結果を残し、復元試験の証跡とその対象版も照合する。証跡が不足すれば利用可能と判定せず、復元試験を本番へ追加実行しない。countsには対象集合、抽出条件、取得時刻を付ける。副作用がないと確認できたdry-runの報告と比較し、対象や時点が違う場合は比較不能とする。daemon稼働中の増減が疑われる場合は、承認済みの整合読取り方法を調査して比較計画を見直し、daemon停止で解決しようとしない。

5. preflightの引継ぎを作成して止まる。backup状態、移行前counts、dry-runの対象別件数、差分と未確認事項を記録する。未実施は未測定、差分未説明は未解決とし、全体を「移行成功」としない。今日はこの様式と不足事項を文書化した時点で終了する。将来preflightが合格しても、旧daemon停止・write migrationの直前が停止位置であり、自動的にcutoverへ進めない。補助資料のfixtureは、この文書境界の検査例としてのみ参照する。

6. 将来のcutoverへの引継ぎ条件だけを記す。別途、旧daemon停止・書込み・必要なschema変更・backfill・smokeの権限、保守時間帯、担当者、復旧責任者、復旧判断基準を確定する。未承認なら手順5の停止状態を維持する。承認後の詳細手順では、旧daemonの停止完了を観測し、直前backupを取り直してからwrite migrationへ進む。停止失敗またはbackup検証失敗なら書込みを開始しない。停止後の整合した基準でdry-run/write/migration mapの件数を照合する設計とし、今日の稼働中countsとの単純一致を必須にしない。write失敗や部分反映時は追加書込みと無条件の再実行を止め、証跡を保全して承認済み復旧手順へ引き渡す。

7. cutover後の保全条件を引き継ぐ。対象版で実在と意味が確認されたmap、link backfill、reprocess分類ごとの件数を同じ対象集合で照合し、対象環境で確定した全キューのclaim・処理結果を承認済みsmoke基準と比較する。キュー数や引数を参考資料の例から固定しない。smokeは実ジョブを動かし得るためpreflightには含めない。旧runtime codeと旧tablesは保持し、live smoke成功、backup artifact、dry-run/write report、backfill完了、旧参照がhistory-onlyであることの証跡が揃っても、削除・dropは別の承認対象とする。どれか未達なら削除せず、差分調査と復旧判断に戻る。

## 完成条件

今日の完成物は、対象と未確定事項、証跡の入手先、preflightの合否、cutover直前の停止位置を含む計画書。daemon停止・書込み移行・smokeの実施結果は未測定と明記し、移行完了やcutover承認を宣言しない。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 今日の計画に外部API・実環境・DB・ファイルの操作がなく、旧daemon停止と書込み移行が実行対象から除外されていれば合格。混入があれば文書を修正する。
3. 将来のpreflightは、対象・版・承認範囲・副作用が確定し、backupとcountsの証跡が対象・取得時刻付きで揃う場合のみ完了。欠落・不一致は未達としてcutoverへ進めない。
4. 将来のcutoverは別承認を必須とし、同じ対象集合・整合した時点でのdry-run/write/map件数一致、backfill照合、対象キューのsmoke成功が必要。不一致や未測定があれば成功扱いせず、削除・dropを止める。
