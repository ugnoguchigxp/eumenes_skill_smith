# 混在キューの再試行条件・待機・検証計画

## 目的

429と恒久的な入力不備を分離し、再試行による混雑を増やさず正常ジョブを進めるための設計・検証計画を作る。今回は文書作成だけであり、実行結果や対象APIとの互換性を保証するものではない。

## 必須原則

再試行は成功条件が変わる見込みと有限の予算がある場合に限る。ジョブ単位の待機とキュー全体の停止は別に扱う。恒久不備は時間経過で直るとみなさず、不明な失敗を成功や破棄に変換しない。

## 操作の境界

現在は外部API、実環境、DB、ファイルへの操作を行わない。将来の接続・変更・再投入は、実施者が対象と権限を別途確認してから行う。資料や発話自体は権限証明にしない。診断では認証情報や入力本文を不用意に複製せず、識別子と必要最小限のエラー情報を使う。

## 標準ワークフロー

1. 対象と開始条件を整理する。将来の実施者は、所有者の運用台帳・承認記録から対象キュー、環境、読み取り／変更／再投入の権限を特定する。対象や権限が不明なら接続・変更へ進まず、既に提供された記録の整理までに留める。キュー製品・版、利用APIの公式資料、既存実装から、状態遷移、取得条件、試行回数の数え方、可視性タイムアウト、Retry-Afterの解釈を調べる。仕様が特定できない箇所は具体APIに置き換えず、実装・投入前で停止する。

2. 失敗を三分する。提供済み記録、または将来承認された読み取りで、ジョブ識別子、エラー種別、発生時刻、試行数、待機指定、入力検証理由、外部処理の完了有無を集計する。429は共有制限範囲と解除見込みを調べる経路へ、仕様・検証器で恒久不備と判定された入力は隔離／要修正へ、不明エラーは保留・調査へ送る。HTTP 4xx全体を恒久不備にしない。修正前の恒久不備は自動再投入しない。原因が未確定なら入力変更やタイムアウト延長を必須修正にしない。

3. 待機規則を定義する。429には、初期待機b、指数増加の上限C、正の最小待機d、最大試行数N、初回からの総時間Tを設定する。第k回失敗後の候補待機はmax(d, U(0, min(C, b×2^(k−1))))とし、Uは各試行で独立に選ぶ。仕様上有効なRetry-Afterがあれば、その下限もmaxに含める。日時形式は時計差を考慮して秒へ換算し、不正値・過去値・欠落の扱いを公式仕様に合わせて決める。長いサーバー待機をCで短縮しない。次回期限が総時間T以上、または試行数がN以上なら自動再試行を終了して診断付き保留へ送る。数値は制限値・処理SLO・滞留許容時間から承認するまで未設定とし、既定値のまま本番投入しない。

4. 状態と取得条件を設計する。待機期限、初回時刻、試行数、診断理由を永続化し、待機への遷移と所有権解放を原子的に扱う。取得可能条件は「期限到達、予算残あり、他の所有者なし」とする。pausedやnextRetryAtは概念上の名称であり、対象製品の実在する機構へ対応付ける。待機中に同じジョブを繰り返し取得・返却する設計は不合格。複数ワーカーで同時取得される場合は導入を止め、取得処理を見直す。入力修正後の再投入は変更履歴と冪等キーを保持し、外部副作用が既に完了していないか判定できなければ再送を保留する。

5. 負荷制御の範囲を決める。制限がAPIキー・テナント・宛先のどこに共有されるかを資料と記録で判定し、その範囲の同時実行数と送信頻度を抑える。個別ジョブの待機だけで共有429が続くなら対象範囲のクールダウンを設計する。範囲不明なら広域停止を断定せず、対象の新規送信拡大を止めて調査する。キュー全体の停止は明示的な運用判断とし、ジョブ失敗だけを理由に自動設定しない。恒久不備の隔離後も正常ジョブを選択できることを合格条件にする。

6. 隔離試験を設計する。references/retry-policy-fixture.mdを待機計算と正負の期待値の確認に使う。その後、実装に対して429の待機指定あり／なし、恒久不備、不明エラー、上限、期限直前／到達時、再起動、複数ワーカー、重複配信を試す計画を作る。期限前取得0件、恒久不備の自動再試行0件、同時所有1以下、重複副作用0件を期待値とする。いずれかに違反すれば本番変更を止める。参照例だけでは実装の合格にしない。

7. 将来の限定導入と見直しを定義する。実施前に変更権限、対象範囲、復旧手順、429率・完了率・最古ジョブ年齢・再試行量の観測窓と許容閾値を承認する。小さな範囲から開始し、429率や滞留が閾値を超える、正常ジョブ完了率が下がる、重複副作用が1件でも出る場合は拡大を止める。新しい送信を抑えつつ記録と隔離ジョブを保持し、復旧時も一括即時再投入しない。許容範囲内の観測が揃った場合だけ段階拡大し、恒久不備は修正確認まで残す。

## 完成条件

429は期限前に再取得されず、恒久不備は同一入力のまま再投入されない設計であること。回数・総時間・共有制限範囲・不明エラーの停止先を決定できること。実環境の適用は権限と仕様の確認後に限定し、判定閾値未達なら拡大を止める。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 文書に429・恒久不備・不明エラーの分岐、待機計算、回数・経過時間上限、権限確認と停止位置があれば計画として合格。
3. 将来の隔離試験では、待機期限前の取得数0、恒久不備の自動再試行数0、同一ジョブの同時所有数1以下、再試行上限超過0を必須とし、違反が1件でもあれば導入停止。
4. 限定導入では事前合意した観測窓・閾値で429率、最古ジョブ年齢、正常ジョブ完了率を比較する。閾値未設定・未測定、または悪化時は拡大しない。
