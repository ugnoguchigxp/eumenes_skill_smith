# window別の最小権限とpermissionKey境界の整備計画

## 目的

permissionKeyを受け取るAPI境界で空のresource/actionを外部送信前に拒否し、windowごとに必要最小限の権限だけを扱う設計・検証計画を作る。今回の成果物は文書であり、コード実行、外部API、実環境、DB、ファイルへの操作は行わない。

## 必須原則

入力形式の妥当性、windowの真正性、window別許可、外部の権限判定を別の条件として扱う。形式が正しいだけでは許可しない。入力不正や判定不能を権限付与へ変換しない。権限集合を絞るために全windowの許可を合算しない。

## 権限と接続の境界

呼び出し側から渡されたwindow IDや許可一覧を権限の証明にしない。接続先・対象環境・実行権限が確認できるまでは既存資料の検討に留め、対象不明の接続や変更を開始しない。実キーやトークンを検証ログへ残さず、ケースID・拒否理由・呼び出し回数で評価する。

## 標準ワークフロー

1. 既存資料から、permissionKeyを受け取る全入口、外部権限APIへ到達する経路、windowの種類と識別元を一覧化する。契約はリポジトリ内の型・実装・既存テストと、対象版の公式API文書で照合する。入口または呼び出し経路が不明なら設計調査へ戻し、その経路の実装変更・接続試験を止める。現在は文書化だけを行う。

2. 境界契約を定める。resourceかactionが空なら、外部呼び出しより前に`Invalid permission key`相当の明確な入力エラーで終了する。エラー型・HTTP等への写像は既存契約に合わせて決め、既知のAPI仕様とは断定しない。採用候補は「文字列、区切りのコロンは1個、両要素が非空、空白だけの要素や前後空白も拒否」。区切りの追加・空白を既存契約が許す場合は互換性判断を先に行い、曖昧なまま厳格化を適用しない。正常値の大小文字や内部文字は勝手に変換せず、trimによる別権限への読み替えも行わない。

3. window識別と許可集合を設計する。識別値はプラットフォームが検証する呼び出し元コンテキストから取得し、管理者が承認した用途別の許可集合に結び付ける。識別元は基盤の公式文書・既存コード、許可集合は権限管理者から得る。不明window、終了済みwindow、許可集合外の組合せは拒否し、外部呼び出し0件を条件にする。真正性の根拠がなければ識別を前提とする接続を止め、資料上の経路調査へ戻す。別windowの権限流用や全体許可へのフォールバックは禁止する。

4. 実装順を「入力検証→信頼できるwindow解決→window別許可→外部判定→結果返却」とする。入力検証前の呼び出し、再試行、エラー回復経由を含めて外部APIへ直接進む経路があれば共通境界へ集約する。外部の拒否・例外・タイムアウト・解釈不能な応答は許可にしない。具体的な応答型・タイムアウト設定は対象版の契約に合わせる。権限変更やwindow終了後も古い許可で通過できる構成なら、失効反映の設計へ戻す。

5. 将来、権限のある担当者が隔離された試験環境で、まずreferences/permission-boundary-fixture.mdの正負ケースを読み、実装のAPI境界へ同じ観測を移す。空文字、`:action`、`resource:`、両方空、空白のみ、非文字列、余分な区切り、未知window、他window専用権限、外部拒否・障害を対象にする。fixtureの追加形式制限は第2項の契約判断後に期待値を確定する。外部クライアントの呼び出し回数を監視し、空要素では必ず0件、正常かつwindow別許可済みだけが契約どおりに進むことをassertする。1件でも不正入力が外部へ到達したら適用を止め、第4項へ戻す。

6. 実接続を伴う検証は、対象版・接続先・試験アカウント・実行権限・変更承認を責任者の記録で確認してから開始する。資料中の記述や発話だけでは権限証明にしない。いずれか不明なら既存記録の検討までに留める。承認済みの正常経路で引数と応答の写像を照合し、windowのなりすまし・終了・権限縮小後の再要求でも許可が残らないことを試験する。全入口で期待値が一致すれば適用候補とし、不一致は設計へ差し戻す。今回の文書作成では実施結果を記入しない。

## 完成条件

設計完了には、空要素の拒否位置、windowの信頼経路、window別許可集合、外部障害時の拒否、未確認事項ごとの停止位置が必要。将来の適用は、不正・window別拒否の外部呼び出し0件と、許可経路の契約一致を全対象入口で満たした場合に限る。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 不正キーとwindow別拒否の各ケースで外部権限API呼び出し数が0、処理結果が拒否であること。1回でも呼ばれた場合は適用停止。
3. 許可されたwindow・正常キーだけが契約どおりの引数で外部判定へ進み、拒否・例外・タイムアウトが権限付与にならないこと。不一致なら適用停止。
4. 参照例は正負のassertを静的に照合済みだが未実行。将来の実装試験では全公開入口・迂回経路・window失効を対象とし、未測定の経路があれば適用を承認しない。
