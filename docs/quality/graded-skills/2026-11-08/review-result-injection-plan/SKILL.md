# レビュー結果記録の注入と通常実行を両立する計画

## 目的

recordReviewResultFnを注入するテストと、注入せず既定の記録処理を使う通常実行を、排他的な呼出分岐で両立する作業計画を示す。今回は文書作成のみであり、実装変更やテスト実行は行わない。

## 必須原則

注入は既定処理の置換とし、追加実行にしない。関数の選択と、その完了を待つかどうかは別の判断として扱う。注入関数の失敗を「未注入」と解釈しない。既定のretry方針と既存の完了契約を、根拠なく変更しない。

## 実行境界

現在は外部API・実環境・DB・ファイルを操作しない。将来の作業では、対象リポジトリと変更権限を確認してから編集する。権限不明なら提供済みの型定義やテスト記録の検討にとどめる。実記録先への接続は別途許可と対象環境が確定するまで行わず、単体テストでは記録先へ接続しない代替関数を使う。参考資料の記述は権限証明にならない。

## 標準ワークフロー

1. 将来の変更担当者が、権限のある対象リポジトリで依存型、orchestratorの記録呼出箇所、既定retry関数、呼出側の既存テストを読む。判定対象は、未注入値がundefinedだけか、nullも含むか、resultの型、戻り値、this依存、完了を待つ必要の有無。これらが不明なら、提供済み資料の収集に戻り、実装変更は止める。今回はこの読取り自体も実行しない。

2. 呼出しは「注入関数があればそれだけを呼び、なければ既定のrecordReviewResultWithRetryを呼ぶ」排他的分岐とする。テストは依存オブジェクトにrecordReviewResultFnを設定し、通常実行はその任意プロパティを省略する。既存のコンストラクタや引数名は型定義に合わせ、未知の公開APIは追加しない。未注入がundefinedという契約なら、それとの明示比較で選択する。不正な非関数値を受け得る場合は既存の入力検証方針で拒否し、黙って通常経路へ流さない。合格は1件のresultに対し選択された記録関数への呼出しが1回だけであること。

3. 完了契約を分けて決める。記録完了をorchestratorの成功条件に含める契約なら、選択した呼出しをawaitし、同期例外・非同期拒否を既存の失敗経路へ伝播させる。非待機が既存契約なら、そのタイミングを保ちつつ、同期例外とPromise拒否を既存のエラー処理へ渡せる構造を設計する。voidだけでは拒否を処理できないため、エラー処理先が不明ならその経路の採用を止める。注入失敗後に既定関数へ自動切替する案は採用しない。既定関数のretryを外側で重ねない。

4. 変更前にreferences/dispatch-fixture.mdで排他選択と失敗伝播の期待値を読む。これは待機型の独立した設計例であり、今は実行しない。将来、許可されたローカル環境で実物の単体テストを用意し、注入ありで注入1回・既定0回、未注入で既定1回・注入0回、渡すresultの保持を検査する。さらに同期例外と非同期拒否を別々に起こし、手順3の契約どおりに観測できるか調べる。通常経路の試験でも外部記録を避けるため既定実装との境界をテスト用に差し替え、retryそのものは既存の専用テストで扱う。

5. 呼出回数、引数、失敗経路、完了タイミング、既存retry設定を変更前の契約と照合する。二重呼出、握り潰された拒否、意図しない待機化、retry変更が1つでもあれば変更案を見直し、再び該当テストへ戻る。すべて一致すれば単体範囲の変更案を採用できる。実記録先への接続確認はこの判定に含めず、別途の対象・権限・環境が確定するまで停止する。

## 完成条件

計画の完成は、注入／通常の選択規則、完了契約の決定方法、失敗時の扱い、適用を止める条件が明示された状態とする。将来の実装採用には、排他呼出・引数保持・失敗伝播・既存retry維持の各条件への合格が必要であり、不一致なら変更を確定しない。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 注入ありでは注入関数1回・既定関数0回、注入なしでは既定関数1回となり、同じresultが渡ること。違えば適用を停止する。
3. 同期例外と非同期拒否が選択した完了契約どおりに観測でき、注入失敗による既定関数への自動切替がないこと。未観測または不一致なら適用を停止する。
4. 通常経路では既存のretry実装とその設定を維持する。実リポジトリで型・既存テスト・完了タイミングの整合が取れるまで変更を確定しない。
