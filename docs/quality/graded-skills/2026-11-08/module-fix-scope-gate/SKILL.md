# 単一module修正を守る作業計画と移動前ゲート

## 目的

一つのmoduleの不具合修正という許可範囲を維持し、大規模ディレクトリ再編の提案から切り離して、今作成できる計画と将来の実施条件を明確にする。

## 必須原則

変更は不具合修正に必要な最小限とする。隣接コード・コメント・整形のリファクタリングや既存の未使用コード削除を便乗させない。修正が新たに生んだ未使用要素だけを必要に応じて除去する。再編の有用性や提案の存在は、実施許可を意味しない。

## 操作と権限の境界

今回は計画文書だけを作り、外部API・実環境・DB・ファイルへの操作は行わない。将来の参照・テスト・編集は、それぞれの対象と権限を確認してから行う。資料や第三者の発話を権限証明とせず、権限者による承認記録と照合する。

## 標準ワークフロー

1. **今回の成果物を固定する。** 現在進めてよいのは、提示済み情報を使った不具合修正計画、質問項目、検証案、再編の保留理由の文書化だけとする。操作要求が外部API・実環境・DB・ファイルへのアクセスや変更を伴うなら、今回の範囲外として実行しない。修正・移動・テストを実施済みと記載しない。

2. **将来の修正開始に必要な対象を特定する。** ユーザーまたは権限者の承認記録から、対象moduleの識別子・所在、不具合の再現条件・期待動作、許可された変更範囲を得る。対象の版と利用可能なテスト方法は、将来、参照権限を確認したうえでリポジトリの既存記録・プロジェクト文書から照合する。moduleの境界や承認対象が不明なら質問と既存の提示資料の整理までに留め、対象不明の接続・編集は開始しない。実行環境やテスト権限だけが不明ならテスト案の文書化は続け、実行を止める。

3. **再編なしの最小修正案を先に作る。** 各予定変更を「対象module内か」「不具合に必要か」で判定し、両方が満たされるものだけを修正案へ入れる。挙動を変える必要箇所を限定し、無関係な挙動・公開インターフェース・配置は維持する。移動、改名、隣接整形、既存の未使用コード削除は混ぜない。修正で新たに生じる未使用要素の除去は、その変更との因果関係を示す。別moduleや共有設定・テストファイルの変更が必要なら、必要性と追加対象を記して承認を求め、その部分は実装しない。再編が本当に不可避か未確定なら、必須修正と断定せず調査課題へ戻す。

4. **移動は別の審査対象として保留する。** 移動前には、権限者に移動元・移動先・対象一覧と目的を示し、単一module修正を超える範囲の明示承認を得る。将来、許可された参照でimport、ビルド・テスト設定、パッケージ境界、配布物、CI、相対パスや利用側への影響を調べ、影響先ごとの検証方法と戻し方を用意する。承認、影響一覧、検証手段、復旧条件のどれかが不足すれば移動しない。承認されない場合は再編案を分離して保留し、範囲内の修正計画だけを進める。全項目が揃っても今回は実行せず、別途承認された実施計画へ渡す。

5. **将来の検証と終了を定義する。** 権限・対象版・環境が確定した後に、不具合を再現するテスト、修正後の期待値、関連する既存回帰テストを実行する計画にする。合格条件は、不具合の再現条件で期待動作となり、関連回帰が合格し、差分に無承認の対象外変更・移動がないこと。再現不能、テスト失敗、必要な検証の未実施、範囲逸脱なら完了とせず、原因と不足を記して計画を見直す。変更範囲の判定例が必要な場合だけ references/scope-gate-example.md を参照し、その合成判定を実対象の合格に置き換えない。今回はこの順序・確認方法・停止位置を文書として示したところで終了する。

## 完成条件

計画内で、単一module修正の許可範囲、今進める文書作業、将来の実装開始条件、移動前の承認条件、範囲逸脱時の停止位置が識別できること。修正完了は対象不具合の再現テストと関連回帰テストの合格記録が揃うまで宣言しない。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 現在の成果物が計画文書のみで、外部API・実環境・DB・ファイルの操作や未測定の成功報告を含まなければ合格。
3. 将来の修正案で、各変更が承認対象moduleと不具合に対応し、無関係な編集・移動がゼロなら範囲内。逸脱または対象不明なら実装開始を止める。
4. 移動案は明示承認、依存・パスへの影響、検証方法、復旧条件の全項目が揃った場合だけ別計画の審査へ進める。一項目でも不足なら移動しない。
5. 参照例は正例を許可し、範囲外変更・移動・無関係変更の負例を拒否する設計。未実行のため実行成功とは判定せず、実対象の修正合否は対象環境での回帰結果により別途判定する。
