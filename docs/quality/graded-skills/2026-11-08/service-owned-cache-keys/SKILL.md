# 業務を解釈しないcacheリポジトリと内部キー生成の設計

## 目的

サービスが業務コンテキストから内部キャッシュキーを決定し、汎用cacheリポジトリを名前空間とキーによる保存・取得・削除に限定する設計計画を作る。今回の成果物は文書であり、実装変更や実環境での操作は行わない。

## 必須原則

結果の同一性を決めるのはサービス、キーを用いて保存するのはリポジトリとする。キー生成は決定的にし、必要な分離条件を欠落させない。namespace は用途・キー形式の区別、key はその用途内の対象識別を担う。リポジトリによる機械的なエンコードは許容するが、業務上の意味による補完や推測はさせない。

## 情報と操作の境界

キーは認可の代替ではない。認可済みのコンテキストからサービスが生成し、秘密や不要な個人情報はキーへ含めない。キーとログの露出範囲も設計対象にする。現在は外部API・実環境・DB・ファイルを操作しない。将来の接続や変更には対象環境と操作権限の確認を要し、参考資料や発話だけを権限証明にしない。

## 標準ワークフロー

1. キャッシュ対象の結果を変える条件を列挙する。将来、権限のある担当者がサービスの呼出元・結果仕様・既存テストから、対象ID、テナント、権限による表示差、言語、データ版などの要否を判定する。「条件が異なっても同じ結果を共有してよいか」を各項目の判定基準にする。判断できない条件は仕様所有者に照会し、キー仕様の確定を止める。既に提供された資料からの設計検討は続けてよい。

2. 依存方向を「サービス → 汎用cacheリポジトリ」とし、サービス内の用途別キー生成関数に業務条件の選択を集約する。提案する境界は保存・取得・削除で共通の `namespace` と生成済み `key` を受けるものとし、保存時には値と合意済みの有効期限指定を追加する。これは設計案であり既存APIの断定ではない。リポジトリが注文種別・ユーザー権限等を読んでキーを補完するなら不合格。リポジトリの責務は共通の型・長さ検査、バックエンド操作、機械的な形式変換に限定する。TTLの業務方針は呼出側、期限の保存・適用はリポジトリ側に置く。

3. namespace に用途とキー形式の版、key に手順1で必要と判断した識別要素を固定順で符号化する。単純な区切り文字連結ではなく、型と要素境界を保つ方式を選ぶ。文字列IDの大小文字や先頭ゼロは、同一視する業務仕様がない限り保存し、勝手に正規化しない。サービス所有の生成関数を保存・取得・削除で共有する。同一条件は同一アドレス、共有禁止の条件差は別アドレスになることを合否基準とする。巨大な入力や秘密をそのまま埋め込まず、ハッシュ化が必要なら入力形式・衝突時の扱いも決める。

4. 将来の実装前に、既存リポジトリの公開インターフェース、利用中のバックエンドと版、キーの長さ・文字制限、TTL単位、削除方法を対象コードと対応する公式資料から照合する。不明ならその項目に依存する変更を停止する。短縮やエンコードが必要な場合も namespace と key の組が曖昧に結合されないことを条件とし、機械変換に業務分岐が混ざるならサービス側へ戻す。

5. 設計レビュー時に references/cache-key-fixture.md を読み、採用する生成規則について同一入力、分離条件、区切り文字、不正入力の正負テストを用意する。掲載例は将来、許可されたローカル環境で実行するためのもので、現在は実行しない。失敗なら生成関数か条件一覧を修正して再検証する。対象実装では、保存後の同一キーでの取得・削除と別テナントからの非取得もテストし、合格前に展開しない。

6. 既存キーがある場合は、旧形式の残存と失効条件を調べ、新namespaceへの切替、必要時だけ旧形式を読む移行、期限による自然失効のいずれを採るか決める。旧読取を採るなら共有範囲の同等性を必須とし、証明できなければ旧値を再利用せず通常の取得元へ戻す。全キー削除は前提にしない。実環境への接続・切替は対象・権限・ロールバック方針が揃うまで止める。責務境界、生成規則、テスト、移行・停止条件の記載が揃った段階で今回の文書作成を終了する。

## 完成条件

サービスとリポジトリの境界、キーに含める条件、保存・取得・削除の共通生成規則、旧キーの扱いが設計上明示されれば文書完成とする。業務条件の漏れやリポジトリ側の意味解釈が残れば承認しない。実環境への適用は、対象契約と権限の確認および対象テストの合格まで停止する。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 設計レビュー：業務条件の選択とキー生成がサービス側にあり、リポジトリに業務オブジェクトの解釈や条件分岐がなければ合格。不一致なら責務分割を修正する。
3. 将来のローカル検証：同一入力の再現性、テナント・対象・版の分離、区切り文字を含む入力、不正入力の拒否について全assert通過を条件とする。失敗した生成規則は採用しない。
4. 実装への適用：実際の保存・取得・削除が同じ生成規則を使い、バックエンドのキー制限と移行方針を満たすことを対象環境のテストで判定する。未測定または不合格なら実環境へ展開しない。
