# 本番DBバックアップの実行・成功確認計画

## 目的

scripts/backup-db.sh による本番DBバックアップの実行順と成功判定を定める。今回提供するのは計画のみであり、実行結果ではない。成果物の生成成功と、復元可能性の検証を区別する。

## 必須原則

対象版の実装と運用契約を判断の基準とし、ZIP・SQLダンプ・SQLiteのいずれかを先に決めつけない。終了コードやファイルの存在だけで成功としない。既存の正常なバックアップを保護し、不確実な状態で再実行しない。

## 本番データと操作の境界

現在は外部API・実環境・DB・ファイルに操作しない。将来の実行には対象と操作範囲に対する明示的な承認が必要であり、資料の記述は権限証明ではない。復元テストは承認された隔離先だけで行い、本番へ上書きしない。ダンプや秘密情報を共有ログへ載せず、成果物と診断記録はアクセス制限された場所に保全する。

## 標準ワークフロー

1. **対象版と入出力を確定する。** 将来、閲覧権限のある担当者が対象コミットの scripts/backup-db.sh、呼び出し先、運用資料を読み、DB種別・接続対象・必要な引数と環境変数・出力先・形式・終了コードの伝播・上書きや削除の有無を記録する。package.json に db:backup がないため、それを実行したり新設したりする計画にはしない。スクリプトと実際の対象設定が一致すれば次へ進む。ZIPかSQLiteファイルか、または対象DBが判別できなければ管理者に照会し、実行前で停止する。既存資料の閲覧・収集は続けられるが、対象不明の接続はしない。

2. **実行の開始条件をそろえる。** 運用責任者から対象DBのバックアップ権限、出力先への保存権限、実行時間帯、負荷・中断基準、隔離復元先を確認する。実装で要求される依存ツールの版、出力先の書込み可否と必要容量、既存バックアップの保護、実行中の書込みに対する整合性確保方式を照合する。承認記録と要件が一致すれば実行可能、不足なら操作せず担当者へ戻す。実装が稼働中DBの単純コピーだけに依存しているなど整合性を説明できない場合は、安全な取得方式をDB管理者と決めるまで停止する。復元照合に使うスキーマ・代表データ・整合性の期待値もここで定める。

3. **承認された方法で一度実行し、終了を記録する。** 起動方法は手順1で確定したスクリプトの契約に従う。未知の引数や別のバックアップコマンドは補わない。開始・終了時刻、対象、版、終了コード、標準出力・標準エラー、実際の出力先を秘密情報を除いて保存する。終了コード0かつ未解決のエラーなしなら成果物検査へ進む。非0・異常終了・所定時間超過・負荷基準超過なら成功判定を止め、承認された中断手順で対処する。途中生成物とログを保全し、上書きリスクや原因を見直すまで再実行しない。

4. **今回の成果物の形式と内容を検査する。** 実行ログの出力先、作成・更新時刻、実行前後の差分を突き合わせ、古いファイルではなく今回生成されたものを特定する。サイズが0より大きく、対象・時刻・形式が期待と一致することを必須とする。過去の正常値からの極端なサイズ変化は原因調査へ戻す。ZIPの場合は承認済みツールでアーカイブの破損検査と一覧確認を行う。「SQLダンプ1件」が対象版の契約なら、その件数と非空を照合する。検査の考え方は references/zip-check-fixture.md を参照する。SQLiteファイルの場合はSQLダンプの件数条件を適用せず、隔離コピーに対して対象版に適合するSQLiteの整合性検査を行い、正常結果を要求する。別形式ならその形式の公式資料に基づく検査を確定してから進む。形式不明、破損、欠落、サイズ0なら生成成功にせず停止する。

5. **復元可能性を隔離先で検証する。** 実行権限と隔離先の識別が確認できた場合だけ、DB種別・版に適合する公式の復元手順で成果物を復元する。アーカイブを展開する場合も、危険なパスや予期しない項目がないことを先に判定する。復元処理の正常終了に加え、手順2のスキーマ・代表データ・整合性の期待値がすべて一致すれば復元検証済みとする。不一致はログと成果物を保全して調査へ戻る。本番への復元、無承認のテスト接続は禁止する。隔離先や権限が未確定なら復元前で停止し、「生成検査のみ合格、復元可能性は未確認」と報告する。

6. **結果を保存し、終了する。** 生成検査がすべて合格なら「生成成功」、隔離復元も合格なら「復元検証済み」と区別して運用記録に残す。運用で定めた保存先・保持期間・アクセス制限と照合し、必要な保存条件を満たさなければ運用上の完了にはしない。失敗または未確認項目があれば、その観測値・停止位置・次の担当を記録して引き継ぐ。既存の正常なバックアップを未検証の今回分で置き換えない。

## 完成条件

生成成功の記録には対象DB、リポジトリ版、実行時刻、終了状態、成果物の保存先とサイズ、内容・破損検査結果を含める。復元検証済みの記録には隔離先と照合結果も含める。いずれかの検査が不合格なら成功扱いを止め、担当者へ引き継ぐ。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 実行記録が終了コード0を示し、ログに未解決の失敗がなく、今回の実行に対応する成果物が確定した場合のみ生成判定へ進む。不明・非0なら停止する。
3. 成果物が想定形式・内容・非0サイズを満たし、形式に応じた破損検査を通った場合に生成成功とする。古いファイルの存在だけでは不合格。
4. 隔離先への復元が完了し、事前に定めたスキーマ・代表データ・整合性の照合がすべて合格した場合に復元検証済みとする。未実施なら復元可能性は未確認と記録する。
