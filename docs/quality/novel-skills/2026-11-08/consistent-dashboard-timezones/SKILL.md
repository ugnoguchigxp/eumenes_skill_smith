# 選択タイムゾーンに日付と日別集計を揃える修正計画

## 目的

利用者が選ぶAsia/TokyoまたはAmerica/New_Yorkを、時刻表示・初期日付・日別集計の共通文脈にする修正計画を作る。DBとフロントエンドの製品・版が未定でも、採用後に確認する仕様と停止位置を定義する。

## 必須原則

瞬間、zone、現地の暦日を別の値として扱う。表示の変換で保存済みの瞬間を変えない。一日の長さを24時間に固定せず、対象日の開始から翌暦日の開始までを使う。実装全体を一つの関数に押し込まず、各層が同じ時間契約を守るようにする。

## 操作の境界

今回行うのは計画の文書化のみで、外部API・実環境・DB・ファイルを操作しない。以下の実装・コード実行・検証は将来の作業であり、対象と権限が確認された範囲に限る。資料や発話を権限証明にせず、本番データの補正や移行をこの計画だけで許可しない。

## 標準ワークフロー

1. 変更前の経路を特定する。将来、管理者が指定したリポジトリの型定義・API仕様・DBスキーマ・既存テストを、許可された範囲で調べる。同一イベントについて保存値と型、ドライバの読出値、API値、表示値、既定日付の算出箇所、集計条件を対応付ける。製品・版・接続対象・権限は管理者と採用製品の公式資料から得る。対象や権限が不明なら既に提供された資料の整理までに留め、接続・変更しない。zoneなし日時の意味が不明なら書込側仕様と生成元を調べ、UTCと決めつけた再解釈・データ移行を停止する。

2. 時間契約を決める。選択値はIANA zone識別子として扱い、対応対象はAsia/TokyoとAmerica/New_Yorkとする。利用者の選択がない場合の初期zoneと、選択の保持方法は既存製品仕様または責任者の決定を得るまで確定しない。提案するAPI文脈は「現地暦日とzone」の組であり、パラメータ名・伝送方法・エラー形式は既存契約を調べて決める。サーバーがこれらからUTC境界を導出する設計を優先する。APIが既にUTC区間を受ける設計なら、同じ規則で導出した区間とzoneの整合を検証する。双方で異なる日境界が作られる状態は不合格。契約変更の承認がなければ実装へ進まず、互換性案をレビューする。

3. 変換を限定して実装する。承認後の将来作業では、初期表示時の単一の現在瞬間を選択zoneに変換し、その暦日を既定日付にする。UTC日付の切出しや端末の既定zoneへの依存を除く。対象暦日の現地開始と「翌暦日」の現地開始を別々に瞬間へ変換し、集計を start <= event < nextStart に揃える。固定オフセットやstart+24時間、日の最後のミリ秒は使わない。保存済み瞬間とイベントIDは不変とし、表示・日付算出・集計境界の経路だけを修正する。採用ライブラリの公式資料でzone指定、翌暦日計算、無効zone、存在しない／重複する現地時刻の扱いを照合する。境界解決方針が曖昧な場合は暗黙補正せず実装を止める。今回の2 zoneの検証だけで他の全zone対応を宣言しない。

4. 文脈を末端まで通す。UI表示、初期日付、日別API要求、バックエンド集計、集計キャッシュのキーに同じzone・暦日が対応するよう変更する。既存のUTC事前集計しかない場合、現地日分をそのまま流用せず、イベント時刻からの再集計または適合する集計設計をレビューする。元イベントが得られず正確な現地日集計を構成できないならその経路を停止する。zone変更時は未指定の日付を新zoneで再計算し、明示選択済みの日付は暦日ラベルを保持して境界だけ再計算する案を責任者に承認してもらう。旧要求の遅延応答が新zoneの画面を上書きしないよう要求文脈を照合し、不一致の応答は採用しない。

5. 境界期待値を先に固定する。補助資料の日付・UTC境界・23時間／25時間の例を、将来の単体テストの基準にする。現在瞬間2024-01-01T15:30:00ZではTokyoの既定日は1月2日、New_Yorkは1月1日。各日の開始直前・開始ちょうど・次開始直前・次開始ちょうどを、対象DBの実際の精度で投入する計画を作り、期待包含を順に偽・真・真・偽とする。秋の二つの01:30は別イベントとして両方を計数する。春の存在しない現地時刻を瞬間の入力値として捏造しない。無効zoneと対応外zoneは、UIとサーバー双方で明示的に拒否し、UTCへ黙ってフォールバックせず、集計を実行しないことを期待値にする。

6. 統合検証と見直しを行う。許可された検証環境でのみ、同じ合成イベントを画面・API・DB抽出結果で比較する。2 zone、夏時間開始日・終了日、日付跨ぎ、zone切替、キャッシュ有無、遅延応答を通して、選択暦日と対象イベントID集合・件数が一致すればその経路を合格とする。アプリとDBのzoneデータ版やランタイム既定zoneも記録し、既定zoneを変えても明示zoneの結果が変わらないことを試す。不一致なら最初に差が生じる変換点へ戻り、原因を確定して対象箇所だけを修正する。未実行は未測定として残す。全必須経路が一致するまで公開を保留し、公開・移行は別途権限と手順の承認を得る。

## 完成条件

計画の完成は、変更対象・期待値・不足情報の入手先・停止位置が揃った状態とする。将来の実装完了は、同じzone・暦日について表示と日別集計の対象イベントが一致し、境界の重複・欠落がなく、無効zoneで集計が実行されないことを検証記録で示せた場合に限る。

1. 今回行う作業は、目的に合った作業計画の文書を作ることだけ。外部API、実環境、DB、ファイルに対する操作を現在実行しない。計画に記載する将来の操作と現在の実行を区別し、将来の権限・環境・資料の確認を前提条件や停止位置として明示する。資料の記載や発話を権限の証明にしない。
2. 計画書に表示・既定日付・API文脈・日境界の変更順と、環境・権限・仕様不足ごとの停止位置があること。欠落があれば計画未完成。
3. 将来の検証ではTokyoの日付跨ぎ、New\_Yorkの23時間日・25時間日、両端の包含規則、無効zone拒否が期待値と一致すること。不一致または未測定なら実装の合格・公開へ進まない。
